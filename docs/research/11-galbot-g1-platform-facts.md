## Galbot G1 (银河通用 Galaxy General Robotics) kinematic structure, and whether a head-frame pose interface with a 14-value arm-joint low-level model is well-defined

### VERIFIED
- [official] Official DoF breakdown: neck 2, arms 7×2, waist 3, leg 2 — 21 articulated joints, excluding chassis and end-effectors
    The official Galbot developer manual (developer.galbot.com, G1 doc v2.2.4, 规格参数 section) gives a table titled 自由度 (excluding chassis and end effectors): 颈部 2, 手臂 7x2, 腰部 3, 腿部 2. Sum = 2+14+3+2 = 21. Note: some AI-generated summaries of this same page mis-add it to 23 or 28 — the table itself sums to 21. A third-party review independently quotes the manual as '21 articulated joints (excluding the four driven wheels and end-effectors)', corroborating the arithmetic.
    NUMBERS: neck 2, arms 7×2=14, waist 3, leg 2; total 21 excluding chassis + EE
    SRC: official spec sheet — http://developer.galbot.com/docs/g1/2.2.4/zh/g1/ ; mirrored verbatim at https://www.robotsj.cn/shiyongshouce/1654.html ; corroborated by https://blog.robozaps.com/b/galbot-g1-review
- [official] DECISIVE: Galbot's own data pipeline defines a 23-D joint vector — leg(5), head(2), left_arm(7), left_gripper(1), right_arm(7), right_gripper(1)
    Galbot's official GitHub repo GalaxyGeneralRobotics/galbot-mcap2lerobot (converts G1 MCAP teleop recordings to LeRobot v2.1) hardcodes the layout in joint_constants.py: indices 0-4 leg_joint1..5, 5-6 head_joint1..2, 7-13 left_arm_joint1..7, 14 left_gripper_joint1, 15-21 right_arm_joint1..7, 22 right_gripper_joint1. The README labels index 5-6 explicitly as 'Head pan/tilt'. robot_type metadata is 'G1_V2.2B'. This reconciles exactly with the manual: SDK 'leg' group of 5 = 腿部 2 + 腰部 3; 21 articulated + 2 gripper joints = 23.
    NUMBERS: 23-D state and action vectors; leg=5, head=2, arms=7+7, grippers=1+1
    SRC: official vendor code — https://github.com/GalaxyGeneralRobotics/galbot-mcap2lerobot (src/galbot_mcap2lerobot/joint_constants.py, README.md)
- [official] DECISIVE: head_joint1/2 and the 5 leg/waist joints are in the ACTION vector, not just the observation — the head is commanded during demonstrations
    In galbot_mcap_to_lerobot.py the action is constructed as `all_frames[i]['action'] = all_frames[i+1]['observation.state']` (line 633) over the full 23-D vector, and generate_modality_json() sets action_names = JOINT_NAMES (all 23). So Galbot's reference imitation-learning pipeline treats neck pan/tilt and the 5 leg/waist joints as commanded action dimensions alongside the arms. The head is therefore NOT a fixed, position-once device in the vendor's own data model.
    NUMBERS: action dim = 23, of which 2 are neck and 5 are leg/waist; only 14 are arm joints
    SRC: official vendor code — galbot-mcap2lerobot/src/galbot_mcap2lerobot/galbot_mcap_to_lerobot.py lines 306-307, 633, 663-667
- [official] Head camera is a STEREO pair mounted on the 2-DoF neck; wrist cameras on both arms
    Manual sensor table: 头部 双目相机x1 (head: one stereo/binocular camera), 躯干 RGB相机x4 + IMUx2, 腕部 深度相机x2 + 腕部六维力传感器x2, 底盘 3D激光雷达x1 + 超声传感器x8 + IMUx1. The ROS topics in the official converter are /front_head_camera/left_color/image_raw and /front_head_camera/right_color/image_raw plus /left_arm_camera/color/image_raw and /right_arm_camera/color/image_raw, all 480×640 @ 30 FPS. The head-left camera is the primary timeline reference for dataset alignment.
    NUMBERS: head stereo 2×(480×640) @30fps; 4 torso RGB; 2 wrist depth; 2 wrist 6-axis F/T; chassis 3D LiDAR + 8 ultrasonic
    SRC: official spec sheet + official vendor code (config.py IMAGE_TOPICS)
- [official] Wrist 6-axis force/torque sensors exist in hardware (2×), but are NOT exported by the official data pipeline
    Hardware spec confirms 腕部六维力传感器x2. However the official mcap2lerobot converter's STATE_TOPICS is only ['singorix/wbcs/sensor'] (joint position/velocity/effort) and IMAGE_TOPICS is the 4 cameras. There is no wrench/force topic in the export path — grepping the converter for force/wrench returns nothing. Joint-level `effort` is available via a use_effort flag, but that is motor torque, not the wrist F/T sensor.
    NUMBERS: 2 wrist 6-axis F/T sensors in hardware; 0 F/T channels in the official LeRobot export
    SRC: official spec sheet + official vendor code (config.py, galbot_mcap_to_lerobot.py)
- [official] Arms are confirmed 7-DoF × 2 — the '7-DoF x 2' assumption is CORRECT
    Confirmed independently by three source classes: the official manual table (手臂 7x2), the official joint vector (left_arm_joint1..7, right_arm_joint1..7), and academic papers ('The Galbot G1 has two 7-DoF arms'; MobileH2R: 'Galbot G1, equipped with an omnidirectional wheel chassis, a 7-DOF robotic arm, a head depth camera, and a wrist-mounted depth camera').
    NUMBERS: 7 DoF per arm, 14 total
    SRC: official spec sheet; official vendor code; papers arXiv:2602.12215 (LDA-1B), arXiv:2501.04595 (MobileH2R)
- [official] Arm geometry and payload
    手臂长（肩部中心到腕部中心）710mm. 工作空间（腕部中心）: 垂直方向 0-2100mm, 水平方向 1900mm. 负载能力（腕部中心）单臂5kg，合计10kg. Marketed arm span 1.9 m and '0-2.4 m' working space (the 2.4 m figure is a marketing reach envelope, larger than the 2100 mm wrist-center vertical figure in the manual).
    NUMBERS: shoulder-to-wrist 710mm; wrist workspace vertical 0-2100mm, horizontal 1900mm; payload 5kg/arm, 10kg total
    SRC: official spec sheet (developer.galbot.com / robotsj.cn mirror)
- [official] Base is a 4-wheel omnidirectional chassis contributing 3 planar DoF; not part of the 23-D joint vector
    底盘形式: 4轮全向移动底盘 (4-wheel omnidirectional mobile base). 底盘尺寸 600mm × 600mm, 投影圆直径 625mm. 底盘最大速度 1.5 m/s. Marketing consistently says '360-degree omnidirectional wheeled base'. Omnidirectional in the plane implies 3 controllable DoF (x, y, yaw) and hence holonomic in the planar sense, but the specific wheel mechanism (mecanum vs. swerve/steered) is not stated. Critically, no base pose or odometry channel appears anywhere in the 23-D state/action vector.
    NUMBERS: 4 wheels; 3 planar DoF (x, y, yaw); footprint 600×600mm, 625mm projection circle; max 1.5 m/s
    SRC: official spec sheet; base DoF count is inferred from 'omnidirectional'
- [official] Torso height is variable over a 650 mm range via the leg/waist group
    腿部升降高度差 650mm ('leg lift height differential 650mm'). Product descriptions call the lower body 折叠腿 / 'high-stability folding legs' combined with the wheeled chassis, and describe a 'single leg' module. This means the 650 mm of vertical torso travel is produced by the 2 leg DoF (plus possibly waist), and the whole 5-joint leg+waist group sits between the chassis and the torso. Marketing frames the result as a '0-2.4 m' reach envelope.
    NUMBERS: 650 mm torso height travel; 5 joints in the leg+waist group (2 leg + 3 waist)
    SRC: official spec sheet; 'folding leg' framing from worldrobotconference.com/expo/product/196.html and baike.baidu.com
- [official] End effectors are swappable, 1 DoF each in the shipped G1 V2.2B config, with CONTINUOUS aperture
    In the official G1_V2.2B joint vector both sides have exactly one gripper joint (left_gripper_joint1, right_gripper_joint1), and the converter divides raw values by 1000 to yield 'meter-scale gripper widths' — i.e. continuous commanded width, not a binary open/close. NVIDIA Isaac Lab's official Galbot asset (galbot_one_charlie) is asymmetric: left_gripper_left_joint/left_gripper_right_joint (parallel jaw, 2 mimic joints) and right_suction_cup_joint1, with TCP links left_gripper_tcp_link and right_suction_cup_tcp_link. Papers report the G1 'is equipped with either a two-finger gripper or 22-DoF Sharpa dexterous hands' — confirming swappability including a high-DoF hand option.
    NUMBERS: 1 gripper joint per side in G1_V2.2B (continuous width, meters); Isaac Lab charlie variant = 1 parallel gripper + 1 suction cup; optional 22-DoF SharpaWave hand
    SRC: official vendor code (joint_constants.py); NVIDIA Isaac Lab source/isaaclab_assets/.../robots/galbot.py and controllers/config/rmp_flow.py; arXiv:2602.12215
- [official] NVIDIA's official Isaac Lab Galbot task expresses all manipulation poses in BASE frame, not head frame
    In IsaacLab source/isaaclab_tasks/.../manipulation/stack/config/galbot/stack_joint_pos_env_cfg.py the observation terms are mdp.object_abs_obs_in_base_frame, mdp.cube_poses_in_base_frame, and mdp.ee_frame_pose_in_base_frame, and the FrameTransformer is rooted at prim_path '{ENV_REGEX_NS}/Robot/base_link'. The reference bimanual Galbot pipeline therefore anchors targets to base_link — a frame that is invariant to neck motion — rather than to the head camera.
    NUMBERS: none stated
    SRC: NVIDIA Isaac Lab repo (isaac-sim/IsaacLab), galbot stack task configs, PR #3210
- [official] Physical envelope, mass, power and compute
    整机高度（最高）1730mm. 机身重量 92.5kg. 电池容量 48V ⎓ 30Ah. 工作时长 8小时. 充电时长 3.5小时 (official adapter). 工作环境 0-40°C, 湿度90% 无凝露. Compute: NVIDIA Jetson AGX Orin 64GB, 275 TOPS (a 'G1 Premium' with Jetson Thor is reported by third-party media). Screen 5.5in 1920×1080, 2× linear 4-mic arrays, 2× 5W speakers, WiFi 2.4/5GHz, BT 5.2.
    NUMBERS: 1730 mm tall; 92.5 kg; 48V 30Ah; 8 h runtime; 3.5 h charge; AGX Orin 64GB / 275 TOPS
    SRC: official spec sheet (developer.galbot.com G1 v2.2.4 规格参数)
- [third-party-media] Third-party/reseller spec pages for the G1 are unreliable and contradict the official manual
    Aggregator and reseller pages variously claim '47 total DoF', '12-DoF dexterous hand', 85 kg or 88 kg mass, 25 DoF, 15 kg payload, 2 h or 10 h runtime, and that the G1 'navigates purely from visual inputs without LiDAR'.     NUMBERS: claimed 47 DoF / 12-DoF hand / 85-88 kg vs. official 21 joints / 92.5 kg

- [third-party-media] Approximate price
    Reported flash-sale pricing ~630,000 RMB (~US$91k) in Feb 2026; standing JD.com listing 690,000-700,000 RMB. One aggregator lists US$55,000 but is flagged 'not verified' and 'prototype stage' — inconsistent with the RMB listings.
    NUMBERS: ~630,000-700,000 RMB (~US$87-97k)

### IMPLICATIONS
  > DIRECT ANSWER — the chain from head camera to arm base is: front_head_camera -> head_joint2 (tilt) -> head_joint1 (pan) -> torso/chest link -> [fixed shoulder mount] -> left_arm_joint1 / right_arm_joint1. That is TWO revolute joints, both of them neck joints, and ZERO of them arm joints. The 5 leg/waist joints and the 3 planar base DoF are COMMON ANCESTORS of both the neck branch and the arm branches, so they algebraically CANCEL out of the relative head->arm-base transform. This is the one piece of good news in the analysis, and it is contingent on the unverified assumption that all 3 waist joints sit below the shoulder mount.
  > QUANTIFIED ANSWER — DoF of the head->arm-base transform NOT observable from the 14 arm joints: 2 joint DoF (head_joint1 pan, head_joint2 tilt). These 2 joints trace a 2-dimensional manifold inside SE(3). Because the camera sits on a lever arm from the neck pivot, pan+tilt vary all 3 translation components and 2 of 3 rotation components of the 6-DoF rigid transform — so roughly 5 of 6 pose components move, and NONE of them are recoverable from arm joints alone. The proposed Model 2 input set (Model 1 output + head image + wrist F/T + 14 arm joints) is therefore STRUCTURALLY MISSING exactly 2 scalars it needs to convert a head-frame target into arm joint commands. The fix is cheap: append head_joint1 and head_joint2 to Model 2's state input (14 -> 16 values). Do this — it is a two-number change that makes the interface well-posed.
  > THE 'HEAD IS FIXED ONCE POSITIONED' ASSUMPTION IS REFUTED BY THE VENDOR'S OWN CODE. galbot-mcap2lerobot sets action[t] = state[t+1] over all 23 dims, so in Galbot's reference teleop recordings the neck is a commanded action dimension that moves within episodes. A pose expressed in the head-image frame is therefore a target in a MOVING reference frame: if Model 1 emits a target at time t and Model 2 executes over the next k steps while the neck rotates, the target physically drifts. You have three options and must pick one explicitly: (a) lock the neck during manipulation and record data that way (simplest, costs you active vision, and needs an SDK freeze-head capability I could NOT verify exists); (b) feed head_joint1/2 into Model 2 and let it re-anchor each step; (c) have Model 1 emit targets in base_link frame instead. Option (c) is what NVIDIA's official Isaac Lab Galbot task does — every pose observation there is *_in_base_frame rooted at base_link.
  > IF YOU EVER NEED AN ABSOLUTE (world- or table-anchored) TARGET rather than a purely body-relative one, the unobservable count explodes from 2 to 10: 2 neck + 5 leg/waist + 3 planar base, none of which appear in the 14 arm joints. Any task where the target is fixed to the environment while the torso lifts or the base rolls (shelf picking across a 650 mm height range, mobile manipulation) will silently break a head-frame-only interface. The 650 mm torso travel is the sharp edge here — it is large enough to change reachability and self-collision feasibility for an otherwise identical head-frame target.
  > MODEL 2's OUTPUT SPACE (14 arm joints) CANNOT REPRODUCE THE VENDOR'S DEMONSTRATION ACTION SPACE (23-D). It cannot command the 2 grippers, the 2 neck joints, or the 5 leg/waist joints. Training a 14-D policy on data collected through the official pipeline discards 9 of 23 action dimensions — including grasp open/close, which is task-critical. At minimum the output must be 16-D (14 arm + 2 gripper). Note the gripper is a CONTINUOUS width in meters (raw value / 1000), not a binary flag, so model it as a regression target, not a classifier.
  > GOOD NEWS FOR MODEL 2's F/T INPUT — BUT IT IS NOT IN THE DEFAULT DATA PATH. The hardware genuinely has 2× wrist 6-axis F/T sensors, so the proposed wrist F/T input is physically available. However Galbot's official mcap2lerobot exporter records only 4 camera streams and the 23-D joint vector from singorix/wbcs/sensor — there is no wrench topic in IMAGE_TOPICS or STATE_TOPICS. You will have to extend the converter yourself to get F/T into your LeRobot datasets. Budget for this; it is not a config flag. (The converter's use_effort flag gives joint motor torque, which is NOT the same signal.)
  > THE '7-DoF x 2' PREMISE IS THE ONE PART OF THE ARCHITECTURE THAT IS FULLY CONFIRMED. Arms are genuinely 7-DoF each, verified three independent ways. But 7-DoF arms are redundant (7 > 6), so a 6-DoF pose target does not determine a unique joint solution — there is a 1-D null space per arm. Model 2 must learn or be given a redundancy resolution (elbow/null-space posture). Since the torso is 650 mm-adjustable and the neck moves, the 'natural' null-space posture in your demonstrations will correlate with torso height — another reason to feed the leg joints in as context even if they cancel from the pure geometric transform.
  > SENSOR PLUMBING IS FAVORABLE TO MODEL 1. The head camera is a STEREO pair (front_head_camera left_color + right_color, 480×640 @30 fps) and the left image is already the primary timeline reference for dataset alignment. If Model 1 must output 3D poses in head-image frame, stereo gives you metric depth without extra hardware. Be aware of the source conflict though: the manual lists the head as 双目相机 (stereo) while MobileH2R calls it 'a head depth camera' — verify on your actual unit whether depth is produced onboard or must be computed.
  > COMPUTE REALITY CHECK. The robot ships with a Jetson AGX Orin 64GB (275 TOPS) onboard. Running both models on an external M4 Mac mini (32 GB) means every control cycle crosses a network hop off-robot and back, on top of a 30 fps camera stream. For a 'cerebellum' that is supposed to close the loop on wrist F/T, that round-trip latency is the dominant design risk — and it is a risk the onboard Orin was specifically provisioned to avoid. Consider Model 2 on the Orin and only Model 1 on the Mac mini.
  > RECOMMENDED MINIMAL CORRECTION TO THE ARCHITECTURE: keep the two-model split, but (1) change Model 1's output frame from head-image to base_link (matching NVIDIA's official Galbot convention and removing the moving-frame problem entirely), or if you keep head frame, (2) add head_joint1/2 to Model 2's inputs; (3) add the 5 leg/waist joints to Model 2's inputs as posture/reachability context; (4) expand Model 2's output to include the 2 gripper widths; (5) extend the official mcap2lerobot converter to carry wrist F/T. None of these are architectural rewrites — they are interface widenings from 14->21 in and 14->16 out.
  > VERIFY THESE THREE THINGS ON YOUR PHYSICAL UNIT BEFORE COMMITTING, because I could not verify them from public sources and each one can invalidate the analysis: (1) obtain the actual G1 URDF from Galbot and confirm that the neck and BOTH shoulders descend from a single torso link with all 3 waist joints below it — if any waist joint sits above the shoulders, the unobservable count rises from 2 to as many as 5; (2) confirm whether the SDK can lock the neck during manipulation; (3) confirm which end effector your unit actually has, since sources contradict each other on suction-vs-gripper and on handedness.

## Galbot G1 (银河通用 / Galaxy General Robotics) — sensors and control interface, evaluated against a two-model "cerebrum/cerebellum" bimanual architecture

### VERIFIED
- [official] Official developer documentation and a public SDK exist — this is NOT a sales-contact-only robot
    Galbot runs a public developer portal (developer.galbot.com) with versioned hardware docs (g1/2.2.4) and SDK docs (SDK/1.7.0), plus a public GitHub org GalaxyGeneralRobotics hosting GalbotSDK. The SDK repo ships a COMPLETE Doxygen-style C++/Python API reference (docs/g1/en/api_cpp_reference/index.html, ~877KB) and ~60 runnable example programs. This is the single most authoritative source and it is fully public — no NDA needed.
    NUMBERS: SDK v1.9.1 (2026-07-03), robot env GBS V1.17, Ubuntu 20-24, Python 3.8-3.14, docs for G1/S1
    SRC: https://github.com/GalaxyGeneralRobotics/GalbotSDK + https://developer.galbot.com/docs/g1/2.2.4/zh/g1
- [official] DECISIVE: the arms accept JOINT POSITION ONLY. Velocity, acceleration and torque commands are explicitly ignored
    Verbatim from the official C++ API reference for set_joint_commands: "For standard joints (head, legs, arms), only JointCommand::position is effective in current versions; velocity, acceleration, and effort are currently ignored." The identical sentence is repeated for execute_joint_trajectory. The JointCommand struct DOES contain position, velocity, acceleration, effort (N·m), Kp and Kd fields — so the interface is shaped for PVT+gain control — but for the arms every field except position is discarded. There is no impedance mode, no variable-stiffness mode, no Cartesian force mode, and no exposed Kp/Kd tuning for arms anywhere in the API.
    NUMBERS: JointCommand fields: position (rad), velocity (rad/s), acceleration (rad/s²), effort (N·m), Kp, Kd — only position honored for head/legs/arms
    SRC: official SDK C++ API reference, GalbotSDK docs/g1/en/api_cpp_reference
- [official] WRIST 6-AXIS FORCE/TORQUE SENSORS ARE REAL AND STANDARD — confirmed twice, independently
    (1) Official hardware spec table lists 腕部六维力传感器x2 (2× wrist six-axis force/torque sensors) as standard wrist-mounted hardware. (2) The SDK exposes them as a first-class API: robot.get_force_sensor_data(GalbotOneFoxtrotSensor::LEFT_WRIST_FORCE / RIGHT_WRIST_FORCE) returning a ForceData struct with force.x/y/z in Newtons, torque.x/y/z in Newton-metres, and timestamp_ns. There is a dedicated example file get_force_sensor_data_example.cpp. This is the developer's key dependency and it HOLDS.
    NUMBERS: 2 sensors (one per wrist); 6 axes each; force in N, torque in N·m; nanosecond timestamps; enum FORCE_NUM bounds the set at 2
    SRC: official hardware spec + GalbotSDK get_force_sensor_data_example.cpp and API reference
- [official] Head is a STEREO RGB PAIR with NO native depth sensor
    Hardware spec says 双目相机x1 (one binocular/stereo camera) in the head. The SDK SensorType enum confirms exactly two head entries: HEAD_LEFT_CAMERA and HEAD_RIGHT_CAMERA, both documented as "typically RGB camera for stereo vision". There is NO head depth camera enum. Depth from the head must be COMPUTED: the SDK has a PerceptionModule enum with FOUNDATION_STEREO and LIGHT_STEREO pipelines ("model sets loaded at init") and an example foundation_stereo_run_once_example.cpp. FoundationStereo is a learned stereo-matching model, so head depth costs GPU inference, not a sensor read.
    NUMBERS: 2 head RGB cameras; 2 stereo-depth pipelines (FOUNDATION_STEREO, LIGHT_STEREO); recorded head streams are 480×640
    SRC: official hardware spec + SDK SensorType/PerceptionModule enums
- [official] Wrist cameras exist and are full RGB-D (RealSense-class), 4 streams per wrist
    SensorType enum per arm: LEFT/RIGHT_ARM_CAMERA (color, "for visual servoing"), LEFT/RIGHT_ARM_DEPTH_CAMERA ("provides RGB-D data for the arm workspace"), and LEFT/RIGHT_ARM_INFRA_CAMERA_1 and _2 (IR stereo pair). The API doc for IrData says "compressed infrared (IR) image data from depth cameras (e.g., RealSense infra1/infra2)" — a direct indication these are Intel RealSense or a RealSense-compatible module. Unlike the head, the wrists give you a REAL depth stream with no inference cost.
    NUMBERS: per wrist: 1 color + 1 depth + 2 IR = 4 streams; 8 wrist camera streams total
    SRC: official SDK API reference SensorType and IrData docs
- [official] Joint state feedback INCLUDES torque and motor current — sensing is far richer than commanding

### IMPLICATIONS
  > MODEL 2 SURVIVES, BUT NOT AS A 'CEREBELLUM'. The position-only finding is decisive: 'For standard joints (head, legs, arms), only JointCommand::position is effective; velocity, acceleration, and effort are currently ignored.' Model 2 can emit 7-DoF×2 joint targets and stream them via set_joint_commands — that part works exactly as designed. But it cannot modulate torque, stiffness or damping. Everything the biological cerebellum metaphor implies about compliance and impedance is unavailable through this interface. Reframe Model 2 honestly: it is a learned redundancy-resolver and trajectory-shaper, not a force controller.
  > THE 'WHAT AN IK SOLVER CANNOT DO' QUESTION HAS A NARROWER BUT REAL ANSWER. Since the actuation channel is identical to what IK would use, Model 2's value must come entirely from choosing BETTER joint targets, not different kinds of commands. On a 7-DoF arm there is a genuine 1-D null space per arm to exploit, plus bimanual coordination, obstacle-aware posture, and matching human teleop style. There is also a concrete gap worth filling: GalbotMotion explicitly 'does not have real-time obstacle perception' and its collision world must be populated manually — so a vision-conditioned policy that implicitly avoids obstacles genuinely beats the shipped planner. That is a defensible thesis. 'Learned compliance' is not.
  > THE WRIST F/T DEPENDENCY HOLDS — CONFIRMED TWICE. This was the stated make-or-break unknown and the answer is yes: standard hardware per the official spec, and exposed via get_force_sensor_data with full 6-axis wrench in N and N·m plus nanosecond timestamps. Model 2's F/T input is legitimate. But note the asymmetry: F/T can only enter as an OBSERVATION that shifts position targets. That makes Model 2 an admittance controller in effect, and admittance quality is bounded entirely by loop rate — which is undocumented. The F/T sensor is only as useful as the rate at which you can react to it.
  > MEASURE THE CONTROL RATE BEFORE WRITING ANY POLICY CODE. This is now the top-priority experiment and it is cheap: loop set_joint_commands with tiny position deltas, timestamp with the nanosecond fields already in JointState, and plot achieved rate and end-to-end lag, from the HPU and from an external PC. Every architectural decision downstream (chunked actions vs per-step, whether F/T feedback is meaningful, whether Model 2 needs to be small) depends on this number, and no document anywhere states it. That the SDK's own 'real_time_control_loop' example is a 1 Hz blocking waypoint demo is a genuine warning sign — do not assume a fast loop until measured.
  > THE MAC MINI PLAN IS BLOCKED AS STATED. The SDK is Ubuntu 20-24 only, with x86-PC-to-ARM-robot cross-compilation as the documented workflow and no macOS target. An M4 Mac mini cannot link the SDK. Three workable options: (a) run inference on the onboard AGX Orin 64GB, which is already there and removes a network hop; (b) put a small Linux box on the robot LAN as SDK host and let the Mac serve inference over a local socket; (c) keep the Mac for training only. Option (a) deserves serious consideration — 275 TOPS and 64GB is a stronger inference target than the Mac for this workload, and it eliminates the PC->XCU/HPU latency you have not yet measured.
  > MODEL 1's INTERFACE IS ALREADY BUILT FOR YOU. set_end_effector_command takes exactly a list of [x,y,z,qx,qy,qz,qw] poses for named end-effector frames, and get_wbc_end_effector_poses returns lee_pose/ree_pose/head_pose. That is Model 1's input and output signature natively supported. This also gives you a strong baseline to beat: pipe Model 1 straight into the WBC and skip Model 2 entirely. If that baseline is good enough, Model 2 has to justify itself against it — run that experiment early, it could save months.
  > HEAD-IMAGE-FRAME POSES NEED A DEPTH DECISION. The head has no depth sensor — only a stereo RGB pair, with depth via the FOUNDATION_STEREO or LIGHT_STEREO learned pipelines. So 'pose in head-image frame' is well-defined for 2D but 3D grounding costs GPU inference on the Orin, competing with your policy for the same compute. Consider: use the raw stereo pair as two image inputs and let Model 1 learn implicit depth (cheap, and the teleop dataset already records both head streams); or exploit the wrist RGB-D, which is real hardware depth with no inference cost, for close-range refinement.
  > THE DATA PIPELINE EXISTS BUT MUST BE EXTENDED — DO THIS BEFORE COLLECTING. galbot-mcap2lerobot already gives you MCAP->LeRobot v2.1 with 4 cameras and 23-D state/action. But it records NO force/torque and NO end-effector poses. Since Model 2 is defined by its F/T input, you must add the wrench channel to both recording and conversion FIRST — retrofitting F/T onto already-collected episodes is impossible. Also note the vendor's action convention is action[t] = state[t+1], i.e. next-frame joint positions at 30 fps: that is the de-facto operating point of the whole platform and a sensible default for both models.
  > 30 Hz POSITION TARGETS IS THE REALISTIC DESIGN POINT — AND IT WEAKENS THE TWO-MODEL SPLIT. Everything converges on ~30 Hz next-frame position control: the dataset fps, the camera streams, the action definition. At 30 Hz a separate 'fast' Model 2 has little room to be meaningfully faster than Model 1, which undercuts the usual cerebrum/cerebellum rationale of a slow planner plus a fast reflex loop. Either find evidence the command path runs much faster than 30 Hz (measure it), or consider a single model with action chunking via set_joint_commands_batch, which the docs explicitly designed for 'VLA inference batch output'.
  > THE 23-D STATE VECTOR IS A FREE UPGRADE FOR MODEL 2. Your design feeds Model 2 only the 14 arm joints. The platform hands you 23 dims including 5 leg/lift joints, 2 head joints and 2 grippers — and on the G1 the 650mm torso lift and the head pan/tilt materially change what the arms can reach and what the camera sees. Feeding the full 23-D state costs nothing (it is already in the dataset) and prevents the policy from being confused by pose changes it cannot observe. Similarly, JointState gives you effort and motor current per joint for free — a useful contact signal that complements the wrist wrench.
  > SENSOR WHITELISTING AT init() IS A REAL BUDGET CONSTRAINT. The SDK warns to 'specify only required sensors to reduce computational overhead and memory consumption', and there are 14+ cameras available. Decide your observation set deliberately and early — enabling both head streams, both wrist colour and both wrist depth streams is already 6 streams and may not be free. get_synced_observation with a chosen anchor camera handles alignment for you, so use it rather than rolling your own sync.
  > COMMERCIALIZATION FACES A CERTIFICATION WALL, NOT A TECHNICAL ONE. No ISO 10218, ISO 13849 PL, ISO/TS 15066, TUV or CE evidence exists for the G1 in any source. For a bimanual manipulator working near people, an uncertified base platform is a hard commercial blocker in most Western markets regardless of how good the policy is. Additionally, the SDK ships hardcoded root credentials (XCU root/<redacted>, HPU galbot/<redacted>) over a flat LAN — that is a security posture no enterprise customer will accept unchanged. Both are procurement questions to raise with Galbot NOW, because neither is fixable in your software layer.
  > TREAT THIRD-PARTY ENGLISH SPECS AS UNUSABLE. Circulating claims contradict the official table on weight, DoF, battery life, and even sensor presence — several sources say the G1 has no LiDAR (it has a 3D LiDAR) and that it has fingertip tactile sensing (it does not). Build the design against developer.galbot.com and the GalbotSDK source only. Fortunately those are public and unusually complete, so the common worry about Chinese commercial robots being sales-contact-gated does NOT apply here — the API reference and ~60 examples are all readable today without buying anything.
  > HIGHEST-VALUE UNKNOWN TO CHASE WITH THE VENDOR: the semantics of LEFT_ARM_PVT_BYPASS_CTRL. The controller names say Position-Velocity-Torque and the JointCommand struct carries effort, Kp and Kd — the plumbing for torque and impedance control clearly exists in the stack, and the SDK just declines to forward it 'in current versions'. If the bypass controller or the raw PublishTarget/SingoriXTarget path exposes torque or gain scheduling, the entire compliance-oriented version of Model 2 becomes viable. ### IMPLICATIONS
  > THE SIM-FIRST GATE IS PASSED, AND SPECIFICALLY ON MUJOCO. Galbot ships an official Apache-2.0 URDF+MJCF+USD with real inertias, real joint/effort/velocity limits, mesh collisions, and tuned actuators — and I verified it loads and runs at ~80x realtime with working offscreen rendering on this exact M4 Mac mini. You can start building Model 1 and Model 2 against the true G1 kinematics today, on the hardware you have, with zero vendor contact. This is a much stronger starting position than most Chinese humanoid platforms offer.
  > BUT YOUR MAC LOCKS YOU OUT OF THE ENTIRE NVIDIA HALF OF THE ECOSYSTEM. The richest G1 sim tooling — first-party Isaac Lab support with 5 registered tasks, RMPFlow controllers, teleop hooks, and Isaac Lab Mimic demo-expansion envs — requires x86_64 Linux/Windows + an NVIDIA RTX GPU. ManiSkill/SAPIEN and therefore RoboTwin are also effectively out (macOS gets CPU-only, and the docs say 'no support for MacOS'). Plan the Mac mini as your MuJoCo development and inference box, and budget for a separate Linux+NVIDIA machine (or cloud) if you ever want the Isaac Lab Galbot tasks, photorealistic rendering, or Mimic-based data amplification. Do not architect as if one Mac is sufficient.
  > YOUR MODEL 1 / MODEL 2 INTERFACE ALREADY EXISTS IN THE VENDOR API — USE IT AS THE CONTRACT. get_wbc_end_effector_poses() returns lee_pose / ree_pose / head_pose and set_end_effector_command() accepts 7-D [x,y,z,qx,qy,qz,qw] pose targets per end-effector frame, while set_joint_commands / set_joint_commands_batch handle the joint layer (with the docs explicitly recommending streaming for 'per-frame model inference output'). Define Model 1's output as exactly that 7-D-per-hand pose and Model 2's output as the 14 arm joint values, and both models plug into shipped APIs. Bonus: you get a free fallback — swap Model 2 for the vendor's WBC/RMPFlow IK to validate Model 1 in isolation before you have any cerebellum at all.
  > BUT CHANGE YOUR FRAME CHOICE, OR AT LEAST DECOUPLE IT. The SDK's EE pose channel is expressed in 'world' (with the head itself as a WBC task), and the RoboCOIN datasets give eef poses in a robot frame — nothing publishes poses in the head-IMAGE frame. Worse, the open-source URDF/MJCF contains NO head camera link at all, so the head-camera-to-head_link2 extrinsic is unpublished and unsimulatable out of the box. Head-image frame is defensible (it makes Model 1 translation-equivariant to head motion), but it makes every dataset and every vendor API require a transform through a calibration you do not yet have. Recommendation: keep an internal head-image-frame representation if you want, but store and exchange poses in a published frame, and treat hand-eye calibration of the head stereo rig as an explicit, early, blocking work item.
  > MODEL 2's WRIST F/T INPUT IS REAL ON HARDWARE BUT ABSENT FROM BOTH SIM AND ALL PUBLIC DATA. The G1 genuinely has 2x six-axis wrist F/T sensors with a clean SDK call returning force (N) and torque (N·m). However: (a) the simulation assets contain no F/T frames — zero grep hits — so you must hand-add MuJoCo <site>+<sensor> elements and guess the mount pose; (b) the official mcap2lerobot converter exports only 23-D joint positions and drops even the effort field that IS present in the source protobuf; (c) the public RoboCOIN G1 datasets have no F/T channel. So F/T is the one Model 2 input you can neither pretrain on public data nor validate in sim without custom work. Either add F/T to your MuJoCo model and your recording pipeline as a first-class task, or design Model 2 to degrade gracefully when F/T is masked — and note that per-joint effort (available in the protobuf and the JointState struct) is a cheaper partial substitute.
  > YOU CAN PRETRAIN BEFORE YOU OWN A ROBOT. ~2,974 episodes / 2.02 M frames / ~18.7 h of real Galbot G1 bimanual data (fold clothes, use dryer, steamer/baozi storage) is downloadable now from BAAI's RoboCOIN on HuggingFace in LeRobot v2.1 format. Critically, it ships eef_sim_pose_state AND eef_sim_pose_action as 12-D both-hands 6-D poses alongside the 21-D joint state and 16-D joint action — that is literally a labelled (both-hands current pose → both-hands target pose) supervision pair for Model 1, and a (target pose + state → joint action) pair for Model 2. This lets you validate the entire two-model decomposition on real G1 data before spending ¥630,000. Do this first; it is the cheapest possible test of your core hypothesis.
  > THE TELEOPERATION STORY IS UNUSUALLY GOOD — AND IT IS ISOMORPHIC, WHICH SUITS YOUR ARCHITECTURE. Galbot sells the TM01, a first-party 7-DoF x2 leader-follower arm pair built for the G1, at ≥100 Hz sampling with ≤20 ms mapping latency, with proportional joint mapping, analog gripper triggers, and built-in episode record / segment / mark-failed / discard buttons with voice feedback. Because it is isomorphic (7-DoF leader → 7-DoF follower), your teleop data is natively joint-space, which is exactly Model 2's output space — no retargeting noise. You get Model 2's labels for free and derive Model 1's labels via FK. This is far better than a VR-controller rig, which would give you EE poses and force you to synthesise joint labels through IK.
  > BUDGET FOR LINUX ON THE COLLECTION AND DEPLOYMENT SIDE REGARDLESS. The GalbotSDK is Ubuntu 20-24 / linux-x86_64 / linux-aarch64 only — there is no macOS build. So the Mac mini can train and can run MuJoCo, but it cannot talk to the robot, cannot run teleop collection, and cannot host deployment. Deployment ultimately targets the onboard AGX Orin (64 GB, 275 TOPS), so size Model 1 + Model 2 for Orin, not for M4 — the M4/32 GB constraint is a training-and-sim constraint, while the real inference constraint is Orin. As a reference point, Galbot's own GraspVLA needs ~9 GB and 200 ms on an L40s; two models in series will be tighter than one, which argues for making Model 1 low-rate (it only decides WHERE) and Model 2 small and fast (it runs at control rate).
  > CHECK WHICH GENERATION YOU ARE BUYING BEFORE COMMITTING TO AN ASSET. The ecosystem is fragmented across generations: the open-source description is 'Golf' (5 leg joints, grippers both sides), Isaac Lab ships 'Charlie' (4 leg joints, left gripper + right SUCTION CUP), the SDK enum says 'Foxtrot', and the data converter reports 'G1_V2.2B'. More importantly, the production G1 is often ASYMMETRIC — one suction cup, one gripper. Your entire premise is 'both-hands pose' bimanual manipulation; if the unit you buy has a suction cup on one arm, half your action space is a binary vacuum toggle rather than a graspable hand, and true bimanual coordination tasks become impossible. Confirm the end-effector configuration in writing before purchase, and specify dual grippers (or dexhands) if bimanual is the point.
  > GALBOT HAS NOT PUBLISHED YOUR ARCHITECTURE — THAT IS BOTH THE RISK AND THE OPPORTUNITY. The strongest possible prior art would have been a Galbot hierarchical model for the G1; it does not exist. GraspVLA is explicitly a UNIFIED end-to-end chain-of-thought (bbox → grasp pose → action chunk) inside one InternLM2-1.8B backbone with chunked end-effector DELTA actions, and its real experiments ran on a Franka Panda, not a G1. Note two things you should steal anyway: (1) intermediate pose supervision inside a single network is a strong baseline you must beat — run it, because if a single model with an auxiliary pose head matches your two-model split, the split is not earning its complexity; (2) their action space is EE deltas with chunking, whereas both the SDK's reference VLA example and the public G1 datasets use ABSOLUTE joint positions — pick deliberately and be aware you are diverging from Galbot's own VLA convention.
  > WATCH THE LICENCES IF COMMERCIALISATION IS THE GOAL. The simulation assets (Apache-2.0) and the mcap→LeRobot converter (MIT) are commercially safe. But GraspVLA's code and weights are CC BY-NC 4.0 — NON-COMMERCIAL — so you cannot ship a product built on GraspVLA weights, and initialising from them likely taints derivatives. The GalbotSDK itself is NOASSERTION (custom licence, not OSI) and needs a read before you build a product on it. Plan to train from scratch or from a permissively-licensed base, and note SynGrasp-1B (their billion-frame synthetic dataset) is still unreleased, so you cannot replicate their pretraining anyway.
  > THE COMMERCIAL PATH IS REAL AND SMALL-TEAM-ACCESSIBLE, WITH A PREDICTABLE SUPPORT COST. The G1 is listed on JD.com at ~¥630,000 (~$87K) and reportedly sold ~300 units in one night after the Feb 2026 CCTV Spring Festival Gala — so this is not a robot available only through Galbot's own retail/pharmacy operations. Support is tiered and priced: FREE (SDK, docs, digital models, GitHub/community), PRO ¥50,000/robot/year (ticketing, remote debug, SLA P0≤4 h, online sim + one-click real deploy), ENTERPRISE ¥200,000/robot/year (dedicated engineer, on-site incl. overseas). For a small team the FREE tier plus the open assets genuinely gets you started, and PRO is a reasonable line item once hardware arrives. Unresolved and worth asking sales directly: lead time, non-China purchase/export, TM01 price, and the head-camera extrinsic + F/T mounting frame you will need for sim fidelity.

## Galbot's own published architecture on the Galbot G1 (GraspVLA / GroceryVLA / AstraBrain / GalbotSDK), and what it implies for a third-party two-model "cerebrum + cerebellum" stack on a G1

### VERIFIED
- [paper] GraspVLA architecture: autoregressive VLM + flow-matching action expert, with a Chain-of-Thought 'Progressive Action Generation' (PAG) chain bbox -> grasp pose -> action chunk
    Trainable LLM is InternLM2 1.8B. Vision encoder fuses FROZEN DINOv2 + SigLIP (OpenVLA-style) through a trainable projector. Action expert is a conditional flow-matching model (pi-0 style). The VLM first emits 2D bounding boxes of the target (supervised on BOTH synthetic action data and internet grounding data), then for synthetic data only it emits a target grasp pose, then the action expert generates the action chunk conditioned on the VLM's KV cache of input + intermediate reasoning tokens. Loss is a plain sum of the autoregressive token loss and the flow-matching loss.
    NUMBERS: InternLM2 1.8B; bbox = 8 tokens; grasp pose = 6 tokens
    SRC: arXiv:2505.03233 (GraspVLA), Sec. 4 + Fig. 3, full PDF text
- [paper] GraspVLA is NOT hierarchical in the developer's sense — it is a single model whose 'levels' are token stages inside one forward pass
    There is no separate high-level and low-level network, no separate control loop, and no pose-target interface between two trained models. The bbox and grasp pose are intermediate CoT tokens inside the same 1.8B VLM, and the action expert reads that model's KV cache directly rather than a serialized pose. There is no way to run the 'upper half' at one rate and the 'lower half' at another.
    NUMBERS: one model, one forward pass; 4 sequential stages internally
    SRC: arXiv:2505.03233 Sec. 4, Fig. 3
- [paper] GraspVLA action space is CHUNKED END-EFFECTOR DELTA actions in Cartesian space; the intermediate grasp pose is in the ROBOT BASE frame, not a camera/head frame
    Paper: 'The action expert is supervised with flow matching loss on chunked end-effector delta actions.' And: 'the VLM further predicts the target grasp pose in the robot's base frame.' Nothing in Galbot's published stack regresses poses in a head-image frame. Proprioception from the latest TWO timesteps is tokenized and inserted before grasp-pose generation, specifically 'to facilitate accurate 3D sensing'.
    NUMBERS: 2 timesteps of proprioception; baselines trained with action chunk = 4; dataset actions stored at 10 Hz
    SRC: arXiv:2505.03233 Sec. 4 and Appendix
- [paper] GraspVLA uses NO force/torque and NO tactile sensing at all — and its own failure analysis names that as a cause of failure
    Inputs are RGB images + text + proprioception only. In the failure analysis on cluttered scenes: 21% of failures involve 'objects with smooth surfaces (e.g., plastic balls) slipping during grasping, which tactile feedback might help resolve.' Other failure modes: 31% hesitation on ambiguous language, 27% misidentification in clutter, 14% occlusion, 7% early gripper closure/collisions.
    NUMBERS: 21% of failures attributed to slip that tactile could fix; 0 force/tactile inputs
    SRC: arXiv:2505.03233 Appendix M (Failure Analysis)
- [paper] GraspVLA runs at roughly 5 Hz effective policy rate, 200 ms latency, ~9 GB VRAM on an NVIDIA L40s
    Head-to-head table vs AnyGrasp explicitly lists 'Ours 5 Hz' against 'AnyGrasp 37 Hz'. Inference time breakdown on L40s: vision encoder 9 ms, bounding boxes (8 tokens) 72 ms, grasp pose (6 tokens) 50 ms, flow matching 64 ms. The autoregressive CoT tokens are the dominant cost (122 of 195 ms), i.e. the 'reasoning' is what makes it slow, not the action head.
    NUMBERS: 200 ms latency; 5 Hz; ~9 GB VRAM on L40s; vision 9ms / bbox 72ms / grasp pose 50ms / flow matching 64ms
    SRC: arXiv:2505.03233 Table 3 + Table 15; GraspVLA GitHub README
- [paper] SynGrasp-1B: 1 billion frames, generated with 160x RTX 4090 GPUs over 10 days
    10,680 object meshes across 240 categories from the Objaverse LVIS subset. Pipeline: antipodal/force-closure grasp synthesis (BoDex), collision-free trajectory planning with CuRobo, physics validation in MuJoCo, then photorealistic ray-traced re-rendering in Isaac Sim. Randomization covers point/directional/dome lights, backgrounds, camera extrinsics (around predefined centers), object pose and scale, and initial robot configuration. Stability filter keeps only grasps that form force-closure under a low friction coefficient.
    NUMBERS: 1e9 frames; 10,680 meshes; 240 categories; 160 x RTX 4090 x 10 days (~38,400 GPU-hours); actions stored at 10 Hz
    SRC: arXiv:2505.03233 Sec. 3 + Appendix
- [paper] ZERO real-robot action data in GraspVLA pretraining — the real:sim ratio is 0:1
    Pretraining is exclusively synthetic action data. The only non-synthetic data is GRIT (internet grounding), and it supervises ONLY the bounding-box tokens autoregressively — never actions. Batches randomly mix the two sources. Internet images are duplicated to match the dual-camera setup and independently augmented (random resize, crop, horizontal flip, color jitter).
    NUMBERS: 0 real action frames in pretraining; 2 data sources (SynGrasp-1B + GRIT)
    SRC: arXiv:2505.03233 Sec. 4 'Joint Training'
- [paper] GraspVLA's real-world robot is a single-arm Franka Panda with a parallel gripper — explicitly NOT the Galbot G1
    Stated limitation: 'Currently, our data generation and evaluation are conducted exclusively on the Franka Panda arm with front and side views. However, our simulation pipeline is inherently scalable and can be readily adapted to other robots and camera configurations. We leave this engineering effort as future work.' Cameras are two EXTERNAL RealSense units (D435 front, D415i side) positioned at the center of the synthetic randomization range — not wrist cameras and not a head camera. Fingers were extended by 2 cm in both sim and real. Workspace confined to 40 x 50 x 20 cm.
    NUMBERS: 1 arm, 7 DoF, parallel gripper; 2 external cameras; workspace 40x50x20 cm; fingers +2 cm
    SRC: arXiv:2505.03233 Sec. 7 Limitations, Sec. 5.1, Appendix
- [paper] GraspVLA zero-shot real-world success ~93% on synthetic-seen categories and ~93% on web-only categories, beating pi-0 by a wide margin
    Real-world, 300 trials. GraspVLA: basic 93.3 / light 96.6 / background 93.3 / distractor 93.3 / height 90.0, SPL 87.2 on synthetic categories; and basic 93.3 / light 90.0 / bg 93.3 / dis 86.6 / height 86.6, SPL 84.7 on web categories. Best baseline pi-0 (without pi-0 pretrain): 80.0 basic / SPL 51.8, and only 40.0 / SPL 36.9 on web categories. Octo and OpenVLA essentially fail (0-20%).
    NUMBERS: 93.3% basic; SPL 87.2 / 84.7; 300 trials; pi-0 best baseline at 80.0/40.0
    SRC: arXiv:2505.03233 Table 1
- [paper] GraspVLA few-shot post-training needs only 10-100 demonstrations per new behavior
    Task 1 (industrial components): 100 demos. Task 2 (mug grasping with a handle constraint / human preference): 100 demos. Task 3 (sequential grasping): 10 demos per bottle. Acknowledgements thank 'colleagues at Galbot for their assistance in collecting and annotating the post-training data', confirming real teleop data is used only at the post-training stage.
    NUMBERS: 100, 100, and 10 demos per task
    SRC: arXiv:2505.03233 Sec. 5.4 + Acknowledgements
- [official] GraspVLA released weights are CC BY-NC 4.0 — NON-COMMERCIAL. No finetuning code is provided.
    README carries the by-nc/4.0 license button. Checkpoint on HuggingFace (shengliangd/GraspVLA) and Baidu Cloud; a StereoVLA variant also released. The repo ships a model server, a sim environment, and a real-robot control interface, but no training or finetuning pipeline — the pitch is explicitly zero-shot use without finetuning. SynGrasp-1B itself is listed 'Coming Soon' and as of the last push (2025-12-29) is still not released.
    NUMBERS: CC BY-NC 4.0; 390 GitHub stars; last push 2025-12-29; dataset unreleased
    SRC: github.com/PKU-EPIC/GraspVLA (README, repo metadata)
- [paper] GraspVLA's real deployment uses a classical Cartesian impedance controller underneath — a hand-written cerebellum, not a learned one
    'We implement a Cartesian-space impedance controller adapted from Franka ROS and SERL Franka Controllers. The architecture converts Cartesian impedance commands into joint-space control via real-time Jacobian-based transformation with singularity handling, while optimizing impedance parameters through system identification.' Multi-step predictions are fed into a receding-horizon scheme in an asynchronous non-blocking architecture, smoothed by a triple-cascaded first-order Butterworth filter (chosen over Bessel/Chebyshev-II/3rd-order Butterworth to avoid overshoot and excessive initial acceleration), with POSITIONAL rather than temporal interpolation to absorb model-latency jitter. Notably, all reported experiments used BLOCKING control; non-blocking was used only for demo recording.
    NUMBERS: triple-cascaded 1st-order Butterworth; receding horizon over the action chunk
    SRC: arXiv:2505.03233 Appendix L (Non-Blocking Control)
- [official] The Galbot G1 has 6-axis force/torque sensors at BOTH wrists, exposed in the official SDK
    galbot_sdk.g1 exposes GalbotOneFoxtrotSensor.LEFT_WRIST_FORCE and RIGHT_WRIST_FORCE via robot.get_force_sensor_data(), returning {'timestamp_ns', 'force': {x,y,z} in Newtons, 'torque': {x,y,z} in N·m}. This is real hardware, first-party, and directly queryable.
    NUMBERS: 2 sensors, 6 axes each (3 force N + 3 torque N·m), nanosecond timestamps
    SRC: github.com/GalaxyGeneralRobotics/GalbotSDK examples/g1/python/galbot_robot/get_force_sensor_data.py
- [official] Full G1 sensor suite per the official SDK: stereo RGB head (no head depth), two RGBD wrist cameras, lidar, ultrasonic, torso IMU, dual wrist F/T
    SensorType enum contains: HEAD_LEFT_CAMERA, HEAD_RIGHT_CAMERA, LEFT_ARM_CAMERA, LEFT_ARM_DEPTH_CAMERA, LEFT_ARM_INFRA_CAMERA, RIGHT_ARM_CAMERA, RIGHT_ARM_DEPTH_CAMERA, BASE_LIDAR, BASE_ULTRASONIC, TORSO_IMU. ### IMPLICATIONS
  > THE BIGGEST FINDING: Model 2 mostly already exists, shipped, in analytic form. GalbotSDK's WBC takes exactly the developer's proposed Model 1 output — both-hands 7-vector poses via set_end_effector_command(poses, end_effector_frames) with get_wbc_end_effector_poses() returning lee_pose/ree_pose/head_pose — and turns it into coordinated whole-body joint motion, backed by IK, FK, Jacobian, collision checking and motion planning, streamable at 125 Hz. Galbot themselves, in GraspVLA, did NOT learn a cerebellum: they used a Cartesian impedance controller with Jacobian transform, a receding-horizon scheme over the action chunk, and a triple-cascaded Butterworth filter. So the developer is proposing to train, from self-collected teleop data, a neural replacement for a component the vendor ships working and the vendor's own researchers chose not to learn. That is the weakest part of the plan and should be the first thing cut. Build Model 1 against the existing WBC; only reach for a learned Model 2 where the analytic one demonstrably fails.
  > THE WEDGE IS FORCE, AND IT IS REAL. The G1 has 6-axis F/T at both wrists (LEFT_WRIST_FORCE / RIGHT_WRIST_FORCE, forces in N and torques in N·m with ns timestamps). GraspVLA uses no force and no tactile, and its own failure analysis attributes 21% of cluttered-scene failures to slip that 'tactile feedback might help resolve'. Galbot's own mcap2lerobot converter — their blessed third-party data path — silently DROPS force/torque from the dataset. So the vendor has first-party force hardware that none of its published models consume and its public data pipeline discards. Contact-rich, force-aware, BIMANUAL manipulation is a genuine hole in everything Galbot has published. That, not 'a better VLA', is the defensible wedge. It also means the developer must extend the recording schema themselves — the 23-D LeRobot state vector has no slot for it.
  > FRAME CHOICE IS A SELF-INFLICTED PROBLEM. The developer proposes poses in the HEAD-IMAGE frame. Galbot's stack works in two other frames: GraspVLA predicts grasp pose in the ROBOT BASE frame, and the SDK's end-effector commands default to the WORLD frame. The G1's head is a 2-DoF pan/tilt joint (indices 5-6 of the 23-D state), so the head frame is time-varying — every Model 1 output would need composing with a live head transform before it can be commanded, adding a latency-sensitive transform the vendor stack never needs. Worse, the head has NO depth sensor (stereo RGB only; hence the FoundationStereo example), so regressing metric 3D pose in head frame means either running a learned stereo model as a third network or guessing monocular scale — while the WRIST cameras have genuine D405 depth. Recommendation: predict in base or world frame like the vendor does, use get_transform()/get_sensor_extrinsic() for the head, and stop paying the head-frame tax.
  > COMPUTE ON THE M4 MAC MINI IS A HARD BLOCKER, TWICE OVER. First: GalbotSDK ships ONLY linux-x86_64 and linux-aarch64 binaries — there is no macOS build. The Mac mini physically cannot talk to the robot without a Linux bridge machine in the loop, which adds a network hop to the control path. Second: GraspVLA is a 1.8B model taking 200 ms and 9 GB on an L40s, yielding 5 Hz — and that is ONE model doing ONE arm's grasping. The developer wants TWO models doing TWO arms on a 32 GB M4. An M4 is far below an L40s in both memory bandwidth and compute. Note also where GraspVLA's time goes: 122 of 195 ms is autoregressive CoT token generation, not the action head. If the developer's Model 1 is a VLM, it inherits that cost. A realistic budget is Model 1 at 1-5 Hz and Model 2 (or the vendor WBC) at 100+ Hz — which, conveniently, is exactly the two-rate split the SDK is designed for (set_joint_commands / publish_target for streaming, with the explicit warning not to use set_joint_positions for model-inference output).
  > DO NOT TRAIN FROM SCRATCH; THE VENDOR'S OWN NUMBERS ARGUE AGAINST IT. SynGrasp-1B cost 160 x RTX 4090 for 10 days — roughly 38,400 GPU-hours — for ONE billion frames of SINGLE-ARM, GRIPPER-ONLY, TABLETOP grasping with no force. A small team cannot reproduce that, and it is not even the right task. But look at the other end of Galbot's own pipeline: few-shot post-training worked with 100, 100, and 10 demonstrations. That is the actionable lesson. The sim-first plan is sound in SPIRIT but should target a narrow, well-randomized bimanual contact task, not a foundation model, and the self-collected teleop budget should be sized in hundreds of demos for adaptation, not tens of thousands for pretraining.
  > THE VENDOR'S MODELS ARE NOT AVAILABLE TO YOU FOR COMMERCIALIZATION. GraspVLA's released weights are CC BY-NC 4.0 — non-commercial — and ship inference-only with no finetuning code, on a Franka, with the dataset still unreleased. GroceryVLA and AstraBrain have no paper, no weights, and no developer API I could find. So 'finetune the vendor model' is NOT actually on the table today for a commercial product. What IS on the table, and is Apache-2.0/MIT and commercially clean: GalbotSDK (Apache-2.0) and galbot-mcap2lerobot (MIT). The existence of an official MCAP-to-LeRobot converter is a strong signal about the intended third-party path: collect teleop on the G1, convert to LeRobot v2.1, and finetune an OPEN model (pi-0 / pi-0.5 / SmolVLA / GR00T-class) — not Galbot's. That is the pragmatic answer to 'vendor model vs. own model': neither extreme. Finetune an open model, in the vendor's data format, against the vendor's WBC.
  > THE VENDOR IS ARCHITECTURALLY BETTING AGAINST YOU — but on no published evidence. AstraBrain is explicitly marketed as a UNIFIED end-to-end brain-cerebellum-neural-control model that '打破了业界将规划、控制、操作模块割裂的传统' (breaks the tradition of splitting planning, control and manipulation into modules). The developer's two-model split is precisely the thing Galbot claims to have transcended. HOWEVER: there is no AstraBrain paper, no model size, no rate, no benchmark, and no interface spec — it is a press claim, not a result. And GraspVLA, the one thing Galbot actually published, is internally staged (bbox -> grasp pose -> action) and externally paired with a hand-written impedance controller. So Galbot's REAL published system is closer to the developer's decomposition than its marketing admits. Do not abandon the split because of the marketing; do reconsider the split because the lower half is already shipped.
  > GRASPVLA'S CoT IS THE DESIGN IDEA WORTH STEALING, AND IT VALIDATES MODEL 1'S SHAPE. The single most transferable result in the paper is Progressive Action Generation: by forcing the model to emit a 2D bounding box FIRST — a target that internet grounding data can also supervise — Galbot got open-vocabulary generalization from a policy trained on only 240 object categories, jumping web-category success from 40.0 (pi-0) to 93.3. The developer's Model 1 ('look at the scene, decide where the hands go') is structurally the same move: an intermediate spatial target that can be supervised from cheap non-robot data. That is the strongest argument FOR the two-level design, and it points at a concrete tactic: co-train Model 1 on internet grounding/pose data so it generalizes past the objects in the teleop set. Note the cost though — those CoT tokens are 122 of GraspVLA's 195 ms.
  > BEWARE THE DEPLOYMENT NUMBERS; THEY DO NOT MEAN WHAT THEY LOOK LIKE. Every headline figure (>95% grasp, >99.97% coffee, 370 orders/day, 5,000 SKUs) is grasp-attempt success or throughput, never task completion, and human intervention rate is NEVER reported in any source in either language. A 40 m² pharmacy with a fixed 6,000-slot planogram is close to a structured-environment pick-and-place problem that the SDK's classical motion planner could largely solve — no source disambiguates whether a VLA is even in that loop. The developer should not benchmark against '95%' as if it were a generalization result, and should assume the real commercial bar is exception rate and intervention rate in an unstructured scene, which is territory nobody has published and where a force-aware bimanual system could genuinely win.
  > PRACTICAL SEQUENCE THIS RESEARCH SUPPORTS: (1) Drop learned Model 2 for now; use the SDK WBC via set_end_effector_command, keep Model 1's output contract as both-hands 7-vector poses so a learned Model 2 can be swapped in later at the same interface. (2) Put a Linux box on the robot side for the SDK; treat the M4 as the Model 1 host at low rate, and budget for the fact that the vendor's comparable model needs 9 GB and 200 ms on a datacentre GPU. (3) Fork galbot-mcap2lerobot immediately and ADD the wrist F/T channels to the schema before collecting a single episode — retrofitting force into an existing dataset is impossible. (4) Use base or world frame, not head-image frame. (5) Size sim-to-real ambitions to a narrow bimanual contact task with GraspVLA-style randomization (lights, backgrounds, camera extrinsics, object pose/scale, initial config), and plan on 100-scale real demos for adaptation, per Galbot's own post-training numbers. (6) Assume you will finetune an open LeRobot-compatible policy, not a Galbot one, because the licence forecloses the alternative.
