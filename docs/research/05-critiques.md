### LENS: Low-level "cerebellum" as redundant re-implementation of exact classical kinematics: is Model B solving a problem that analytic IK + servo already solves exactly, sub-millisecond, with guarantees — and is its RGB input a tell that its stated job is not its real job?

[FATAL] Model B's I/O signature (target EE pose + current joint values → joint commands) is literally the signature of inverse kinematics plus a servo loop. That is MoveIt Servo. It already exists, runs at 100–250 Hz publishing into a 500–1000 Hz ros2_control loop, is exact to machine precision, needs zero training data, and is auto-generated from the URDF.
  WHY: IKFast produces closed-form analytic solutions in ~5–50 µs and enumerates every branch. TRAC-IK solves >99.8% of queries in sub-millisecond time (vs ~96% for stock KDL, which fails at joint limits). Damped-least-squares differential IK is a single 6×N pseudo-inverse — microseconds. Against this, the best case for a 100–300M-parameter RGB-conditioned Model B on an M4-class Mac mini is ~15–40 ms (25–60 Hz), i.e. 500–8000× slower, and learned IK is measurably LESS accurate: IKFlow reports millimeter-level translation error and up to ~1.5° rotation error, and CycleIK needs a downstream classical optimizer to reach sub-millimeter. You are trading exactness for approximation and paying 3–4 orders of magnitude in latency for the privilege. The research confirms this is not a gap in the literature — it is an absence: RT-Affordance's low level is Cartesian, HiRT outputs EE deltas, TRI's LBM outputs relative SE(3) with 6D rotation, GR00T N1.6 explicitly ABANDONED absolute joint angles for state-relative chunks, and π0.5 commands joint targets tracked by 'simple PD controllers... without any additional trajectory planning'. No published hierarchical VLA asks a learned low level to convert a Cartesian target into joint commands.
  FAIL: Task: 'insert the USB-C connector into the port.' Model A emits a target EE pose. Classical path: TRAC-IK (<1 ms) + Cartesian impedance at 1 kHz, closing on force. Learned path: Model B runs at ~30 Hz with ~1–3 mm regression error, stacked on top of the ~2.1 mm RMS / 3.2° hand-eye calibration bias already baked into Model A's absolute pose. USB-C clearance is sub-millimeter; the peg-in-hole literature is explicit that when 'tolerance and the robot's precision are at the same level, small errors are significantly amplified, leading to jamming.' Model B fails the task while consuming most of your parameter budget, and — because it emits joint POSITIONS — it cannot express compliance, so it also cannot recover the way a 1 kHz impedance controller would.
  FIX: Build the classical baseline first and make the split earn its existence against it: Model A (RGB → target pose) → TRAC-IK with null-space posture bias → ros2_control at 500–1000 Hz (Cartesian impedance if the hardware is torque-capable). This is a weekend of integration and zero training data. Only if a measured deficiency survives should Model B exist — and then as a clipped RESIDUAL added to the classical output (q_cmd = IK(pose, seed=q_prev) + clip(f_θ(·))), following Kawato's feedback-error-learning and the residual-RL line (Johannink et al. ICRA 2019), not as a replacement.

[FATAL] Inverse kinematics is multi-modal (up to 8 branches on a 6-DoF arm, a 1-D null-space manifold on 7-DoF). A learned regressor has no mechanism to pick a branch consistently, so it will either output the arithmetic MEAN of two valid branches — which is not a valid solution at all — or, if it is a diffusion/flow head, sample different branches on consecutive timesteps. Both produce joint-space discontinuities that classical IK structurally cannot produce, because IK is seeded with q_current and selects the nearest branch.
  WHY: This is the sharpest technical failure and it is invisible in offline MSE. An L2-trained network fitting a multi-modal target converges to the conditional mean; the mean of an elbow-up and an elbow-down solution has a forward kinematics that is nowhere near the commanded pose. A stochastic head avoids mode-averaging but replaces it with mode-switching: nothing in the training objective enforces temporal consistency of branch choice across timesteps. Analytic IK sidesteps this entirely by enumerating solutions and picking argmin‖q − q_current‖ — a hard continuity guarantee no imitation objective provides. The research shows the field has actually measured the analogous pathology: HDP found its pose-outputting diffuser had a 24.55% IK error rate, and the 'Demystifying Action Space Design' study gives a theoretical argument that step-wise integration amplifies noise as O(k). Note also that this failure gets WORSE with more demonstration data, since more data means better coverage of both branches.
  FAIL: Task: 'pick up the mug on the far left of the table and place it on the far right.' Crossing the workspace midline on a 6-DoF arm forces a shoulder/wrist configuration flip. Your teleop demos contain both elbow-up and elbow-down executions of nearly identical target poses. At the branch boundary Model B's output either (a) collapses to a mid-configuration whose FK is 15 cm off the target and whose gripper is pointing sideways, or (b) flips branch between t and t+1, commanding a ~180° wrist slew in one 33 ms control step. The arm either whips the mug across the room or trips a velocity-limit fault. You will misdiagnose this as 'needs more data' and it will never converge, because the target is genuinely bimodal.
  FIX: Do not learn the pose→joint map. If a learned component must influence configuration choice, learn only the DISCRETE PREFERENCE over exact analytic solutions (which branch / which arm-angle), which is what the ML-for-analytic-IK literature actually does — the kinematics stays exact and the network only picks. On 7-DoF, express the choice as one scalar: have Model A emit pose + swivel angle (the ERJ formulation), then solve exactly.

[MAJOR] Feeding RGB into Model B is the design's biggest tell that its stated job is not its real job — and it is also the single most expensive choice on the intended hardware. If Model B's job is kinematic, the image is redundant: the target pose plus the joint vector fully determine the answer. If the image is genuinely load-bearing, then Model B is not doing IK and the design is mis-specified.
  WHY: Three candidate justifications exist and each collapses on inspection. (a) Collision-aware null-space resolution — but RGB is the wrong modality (you need geometry; use depth/pointcloud), and cuRobo/QP-IK/OMPL do this with an explicit collision model and, for sampling-based planners, probabilistic completeness — a guarantee no network provides. (b) Visual servoing to cancel Model A's calibration bias — this is the ONE legitimate use, but then Model B is a visual servo, must take its goal in IMAGE space (not as a metric pose that already inherits the calibration error you are trying to cancel), must run at camera rate, and must be benchmarked against classical uncalibrated IBVS with online Jacobian estimation, which already solves calibration-free servoing without learning. (c) Contact/task phase — not expressible at all if the hardware accepts only joint position commands. Meanwhile the cost is severe: VLA-Perf's per-stage breakdown shows the vision encoder + VLM dominate latency (π0 on Thor: vision 6.06 ms + VLM 20.30 ms + action 26.20 ms). Apple silicon is ~7 FP16 TFLOPS on an M4 Pro vs 165 on a 4090 — you are paying the compute-bound cost TWICE on the platform worst at compute-bound work. And a camera-fed Model B is capped at camera frame rate (30–60 Hz) no matter how fast the accelerator is, which destroys the 200 Hz reflex-layer story outright. OpenHelix's probing of the latent in real dual-system VLAs found it 'largely insensitive to changes in visual information' — the field's own evidence that these vision channels often do not carry what designers assume.
  FAIL: Task: bin-picking from a cluttered tote with a wrist camera and an overhead camera. You budget Model A at 3 Hz and Model B at 100 Hz. In reality: two 640×480×3 frames = 1.8 MB/cycle through a second full vision encoder; on an M4 Pro Model B lands at ~25–40 Hz, and MLX's single Metal dispatch queue per process (GitHub ml-explore/mlx #3078, closed without fix; multi-process MLX hangs ~1 in 200–400 calls under GPU saturation) means Model A's 300 ms forward pass head-of-line-blocks Model B. Measured p99 latency for the 'fast' loop equals Model A's inference time, ~300 ms. Total serialized latency = latency(A) + latency(B), which is strictly WORSE than a single monolith of the same total size. You have paid for a hierarchy and received a slower monolith.
  FIX: Delete RGB from Model B unless you can state, in one sentence, which of (a)/(b)/(c) it serves — then design and benchmark for that specific job. If the answer is (b), rebuild it as an image-space visual servo with an image-space goal and compare against classical uncalibrated IBVS. Otherwise feed Model B proprioception + wrench + at most a small low-res wrist crop, or share Model A's cached visual features (the corticopontine pattern — the biological cerebellum receives cortically-abstracted input via the pontine nuclei, never raw retina). On Mac specifically: Model A in MLX on GPU, Model B compiled to Core ML pinned to cpuAndNeuralEngine with GPU explicitly excluded — verify ANE residency with the Core ML performance report, do not assume it.

[MAJOR] Putting a learned network in the exclusive command path removes every safety property the classical stack provides and gives you no way to get them back. There is no hard joint-limit constraint, no velocity/torque bound, no reachability check, no singularity behavior guarantee — a network output is an unbounded vector, and clipping it silently produces pose error with no error signal.
  WHY: QP-formulated IK (iKinQP, TSID, pink/pinocchio) enforces joint limits, velocity limits, and collision constraints as HARD constraints while re-optimizing the task within the feasible set — a network can only approximate this, and it approximates worst exactly where it matters (near limits, near singularities, at unreachable targets), because those regions are under-represented in demonstration data by construction. Damped-least-squares degrades gracefully at singularities by design (λ damping); a regressor extrapolates arbitrarily. The biological analogy you invoked actually argues against this topology: the real cerebellum has NO direct output to motoneurons — its only outputs are deep cerebellar nuclei → thalamus → cortex and → red nucleus/reticular formation. Its ablation produces ataxia and dysmetria, not paralysis. Delete Model B and your robot is inert. A module whose ablation causes paralysis rather than incoordination is the corticospinal tract, not a cerebellum.
  FAIL: Task: 'pick up the plate from the drying rack.' Model A, on a novel scene, hallucinates a target pose 8 cm inside the countertop — a routine failure mode given the ~2 mm/3° calibration budget plus perception error, and exactly the failure GHOST's oracle ablation quantified. With classical IK you get an explicit reachability/collision rejection and can trigger replanning. With Model B you get a plausible-looking joint vector that drives the gripper into the counter at whatever speed the position controller will deliver. There is no layer that can detect this, because Model B IS the bottom layer.
  FIX: Insert a fixed, non-learned reflex layer BELOW both models, in code not weights: joint position/velocity/torque clamps, workspace bounds, reachability + collision filter on Model A's pose before it is ever consumed, force-threshold retract. This runs at ros2_control rate, is verifiable, and is what actually justifies the word 'hierarchy'. Additionally, restructure Model B as an additive residual so residual→0 recovers a working classical controller — the graceful-degradation signature that matches the biology you are invoking.

[MAJOR] The interface itself — an ABSOLUTE SE(3) pose — is the worst-scoring of the four canonical action abstractions in the only clean head-to-head measurement available, and on a redundant arm it is underdetermined. Both problems are fixable with arithmetic, not with a neural network.
  WHY: Single-arm AgileX, ACT-regression, average progress score: EE absolute 69.0%, joint absolute 77.3%, joint delta 88.0%, EE delta 89.6%. Chunk-wise delta beats step-wise delta by ~10 points with an O(k) vs O(1) noise-amplification argument behind it. So the quantity you are handing to Model B is ~20 points below the best available choice before Model B does anything. Separately, on a 7-DoF arm an EE pose does not determine the arm: the ER/ERJ study measured joint space (oracle) 96%, ERJ (pose + one redundancy scalar) 94%, pure task space 8% on five confined-space real-world tasks, with 0% on 'take cup out of cabinet' — the elbow drifts and collides. The fix that recovers 8%→94% is ONE additional number (elbow arm-angle or the redundant joint), not a learned network. Absolute pose also inherits the full ~2.1 mm RMS / 3.2° hand-eye calibration bias as a systematic, uncorrectable offset that Model B cannot see.
  FAIL: Task: 'take the cup out of the upper cabinet' on a 7-DoF Franka. Model A emits a correct grasp pose at the cup. Model B, having never been shown that this particular pose requires elbow-down, produces an elbow-up configuration; the elbow contacts the cabinet frame, the arm stalls against the shelf, and the position controller winds up torque against a rigid obstacle. This is precisely the 8%-success regime the ER paper measured, and it is a redundancy-resolution failure, not a perception failure — no amount of RGB into Model B fixes it, because the information needed (which null-space solution is collision-free) is geometric, not visual.
  FIX: Change the interface to a chunk-wise SE(3) DELTA (relative to the pose at chunk start) with 6D continuous rotation representation (never Euler, never raw quaternion), plus gripper command, plus duration/velocity scale, plus — on a 7-DoF arm — an explicit swivel-angle/redundancy scalar, plus — for any contact task — a stiffness channel or at minimum a 3-level compliance flag. Then solve exactly. This captures nearly all of what a learned Model B could plausibly offer, at zero latency cost, with no training data.

[MAJOR] You are allocating capacity to the half of the system that is already near-saturated. The published oracle ablations say the residual error lives almost entirely in the high level, and that a ZERO-parameter classical low level is already good enough.
  WHY: GHOST froze the low-level policy and swapped only the high level: fold-towel went 36.7% → 90%. The authors' own conclusion is that the bottleneck is high-level goal prediction, not low-level execution. RT-Affordance: predicted affordance 68% vs oracle affordance 76% — the low level was never the constraint. And the entire keypose family (PerAct, Act3D, RVT, RVT-2) achieves precise manipulation from ~10 demos/task with a low level that has ZERO learned parameters (a classical motion planner). Meanwhile the strongest hierarchical splits in production are wildly asymmetric — Helix 7B/80M, RoboDual 7B/20M trainable, π0 3B/300M — and when NVIDIA wanted more performance in GR00T N1.6 they doubled the low-level DiT AND froze more of the high level, which is a training-recipe change, not a capacity-split argument. Nobody splits 50/50, and nobody in this literature spends low-level capacity on kinematics.
  FAIL: You spend six weeks training a 200M-parameter Model B. On a 15-task evaluation it scores 62%. You then run the control: same Model A, Model B replaced by TRAC-IK + null-space posture bias + Cartesian impedance (zero training). It scores 61%. The 1-point gap is inside the noise band — TRI needed 50 real rollouts per task per condition and 1,800 total trials with Bonferroni correction to separate policies, and HiRT's hierarchical-vs-monolithic gap on real quasi-static tasks was 1.3 points (70.0 vs 71.3, hierarchy WORSE). You cannot distinguish your two designs and you have learned nothing from six weeks of work.
  FIX: Put the parameters in Model A and give it the data advantage that actually made the split pay elsewhere: RT-Affordance's affordance predictor collapsed from 77% → 24% without ~750 cheaply hand-annotated images and → 11% without web co-training. That is where the split's leverage lives. Then plan the evaluation before the architecture: build the classical-low-level baseline first, test on DYNAMIC scenes (moving targets, disturbances) where every paper's hierarchy advantage actually appears, and budget enough trials to have statistical power.

[MODERATE] Training Model B on demonstration-derived ground-truth poses and then deploying it on Model A's error distribution is a textbook covariate shift, and this specific gap has been measured repeatedly in the double digits.
  WHY: IK does not have this problem: it is correct for every reachable target in the workspace by construction, including targets no demonstration ever visited. A learned Model B is correct only on the thin manifold of (pose, joint-config) pairs its training data covered, and Model A's outputs at deployment are systematically off that manifold — biased by calibration error, shifted by novel scenes, occasionally infeasible. GHIL-Glue isolated exactly this handoff and recovered +25% on CALVIN and 54% → 70% on a real robot purely by filtering non-progressing subgoals and de-synchronizing augmentation so the low level tolerated the high level's artifacts. OpenHelix found that without projector pre-alignment between two separately-pretrained models, EVERY configuration scored 0/0/0/0/0. The hierarchical-RL literature names the same thing formally: 'the higher-level policy takes the same action under the same state but could receive markedly different outcomes because of the low-level policy changing.'
  FAIL: Task: 'open the drawer.' Model B was trained on handle poses extracted from human teleop, which are always within ~5 mm of the true handle. At test time Model A predicts the handle pose 2.5 cm high on a drawer it has not seen. IK would still produce a valid, exactly-correct joint solution for that (wrong) pose, and the resulting failure would be a clean, diagnosable 2.5 cm miss you could trace to Model A. Model B instead produces a joint vector from an off-manifold input and misses by 7 cm in an unrelated direction, with the gripper mis-oriented — you now cannot tell whether the failure was perception or execution, and the interface has stopped being the debuggable asset that was its main justification.
  FIX: If Model B survives at all: after Model A converges, roll A out on the training scenes and retrain/finetune B on A's ACTUAL predicted poses (a DAgger round on the interface), plus noise/perturbation augmentation on the target pose during B's training. Also train B to consume STALE targets from day one — HiRT explicitly caches the latest high-level output and trains the low level against it; if you train synchronously and deploy against a 300 ms-old pose from a Mac-hosted Model A, expect overshoot and limit-cycle oscillation near contact and expect to misdiagnose it as a modelling problem.

[MODERATE] The proposal never states whether Model B is doing inverse kinematics, motion planning, or visual servoing. These are three different problems with three different classical baselines and three completely different justifications for learning — and the ambiguity is why the design looks defensible.
  WHY: If B maps a pose to joints instantaneously, its baseline is IKFast/TRAC-IK (µs, exact) and it loses on every axis. If B generates a collision-free joint TRAJECTORY toward the pose, its baseline is OMPL/cuRobo/CHOMP, and here there IS genuine counter-evidence: HDP scored 80.18% on RLBench vs PerAct+Planner 57.72%, and its RK-Diffuser hit 94.55% with oracle goals vs RRT's 26.82%. But read that carefully — HDP's win came from being KINEMATICS-AWARE (joint output distilled from a pose diffuser via differentiable forward kinematics), and the planner baseline was an RRT that scored 26.82% even with ground-truth goals, i.e. the sampling-based planner's jerky non-repeatable output was the problem, not IK. And if B is doing visual servoing, its baseline is classical uncalibrated IBVS with online Jacobian estimation, and it must take an image-space goal. Each framing demands a different input set, a different output space, a different training signal, and a different benchmark.
  FAIL: You build Model B against an implicit 'motion planning' intuition (it should avoid the shelf) but train it on demonstration data that contains almost no near-collision configurations, and evaluate it on reaching tasks where IK alone suffices. It looks fine. Then on the first genuinely cluttered task — 'retrieve the bottle from behind the cereal box' — it produces a straight-line joint interpolation through the cereal box, because 'avoid obstacles' was never in the loss and RGB alone never gave it the geometry. You conclude the architecture needs more capacity; the actual problem is that you never decided what the module was for.
  FIX: Write down Model B's job in one sentence and pick the matching classical baseline before writing any training code. If it is IK: delete Model B. If it is collision-aware trajectory generation: benchmark against cuRobo (GPU-parallel IK+planning) and QP-IK with collision constraints, and give the model DEPTH/pointcloud, not RGB. If it is visual servoing: give it an image-space goal, run it at camera rate, and benchmark against classical uncalibrated IBVS. If it is compliance adaptation: verify first that your hardware exposes a torque or variable-stiffness interface — if the arm accepts only joint position commands, this justification is void and Model B has strictly nothing left to offer over IK.

[MODERATE] The 'split capacity to improve performance' rationale is not what any of the supporting literature actually tested, and the one lab that tested it directly found the benefit lives in the training data, not the runtime split.
  WHY: π0.5's ablation: the second-best configuration was 'implicit HL' — NO high-level inference at runtime, but subtask-prediction data still in the training mixture. The authors' verbatim conclusion: 'a significant portion of that benefit is already obtained simply by including subtask prediction data in the training mixture.' HiRT's real-world quasi-static average: hierarchical 70.0 vs monolithic 71.3 — the split was slightly WORSE, and won only on dynamic tasks where 4.1 Hz was the binding constraint. OpenHelix's asynchrony sweep found running the high level every step vs once per 60-step episode barely changed success (94/97/95/95/95/95/95). The MoE scaling-law literature — the only rigorous study of whether splitting capacity beats one model — found routing gains 'diminish with model size' and that reasoning SATURATES with more experts while a slightly wider dense model solves problems no number of experts can. And every dual-system that does win passes a LEARNED LATENT with gradients crossing the boundary (Helix backprops S1→S2; GR00T is 'tightly coupled and jointly optimized'; FiS-VLA's entire contribution is UNDOING the two-separate-models design because separateness 'limits System 1 from fully leveraging the rich pretrained knowledge').
  FAIL: You ship the two-model split and it matches your monolithic baseline. Post-hoc you run the π0.5-style control: one model, one forward pass, with target-pose prediction as an auxiliary loss head. It matches or beats the split at half the inference latency, no interface, no covariate shift, no second dataset, no MLX queue contention. The decomposition was a useful training signal all along; you paid for it in architecture instead of in a loss term.
  FIX: Run that control experiment FIRST — it is roughly a one-week job and it is the cheapest possible test of your core hypothesis. Train one model with an auxiliary target-pose prediction head and compare against the split on identical data. Simultaneously, kill the control-rate justification the cheap way: action chunking + Real-Time Chunking / SmolVLA-style async execution turns a single 3 Hz backbone into a smooth 30–50 Hz command stream with equal success rates, ~30% faster completion, and 2× throughput — no second model, ~50 lines of code. If those two experiments close the gap, the split has nothing left to justify it.

### LENS: The hand-designed 6-DoF end-effector pose interface as a lossy information bottleneck and a source of compounding error — attacking what a pose target cannot express, what happens when Model B is trained on ground-truth poses and deployed on Model A's noisy ones, the non-differentiability of the seam, frame/calibration error propagation, and whether two smaller locally-trained models generalize better than one bigger one at a fixed data budget.

[FATAL] A bare SE(3) pose is not an action. The interface as specified carries no gripper command, no duration/velocity, and no task-phase bit, which makes Model B's learning problem formally ill-posed at exactly the moments that decide task success.
  WHY: For a single grasp, the mapping (target_pose, joints, RGB) -> joint_command is multi-valued at the same target pose: approach-with-gripper-open, close-gripper, lift, and release all occur at or near the same SE(3) target, and a wrist-camera crop barely distinguishes them. A regression or diffusion head trained on that data either averages the modes (partially-closed gripper) or must re-infer task phase from RGB — i.e. Model B silently re-does Model A's semantic job with a smaller, non-language-conditioned model. Every published pose-interface system includes the gripper bit in the interface as a first-class channel: HDP's interface is literally (a_trans, a_rot, a_grip); RT-Affordance's affordance keyframes are auto-extracted at the timesteps where gripper state flips; HAMSTER's 2D path is annotated with gripper open/close. Timing is equally load-bearing and equally absent: a waypoint with no duration is not a trajectory, so Model B must invent approach speed, and approach speed is what determines impact force at contact.
  FAIL: Task: 'pick up the red mug from the counter and put it in the sink.' Model A emits the correct grasp pose on the handle. At t=0 the right action is approach with the gripper open; ~400 ms later, at essentially the same pose and a near-identical wrist image, the right action is close. Model B sees two training clusters with the same conditioning and different labels, and emits a half-closed gripper during approach — it knocks the mug over before contact detection fires. On the return leg, the same ambiguity at the place pose causes an early release and the mug drops into the sink from 8 cm. The interface log shows a perfectly correct pose the whole time, so the failure is undebuggable at the seam you built specifically to be debuggable.
  FIX: Widen the interface to the minimum executable unit: a chunk of 8-16 waypoints, each carrying (6D-rotation SE(3) delta, continuous gripper aperture, dt or velocity scale), plus a discrete phase/compliance flag. This is ~15-20 numbers per waypoint, not 6. HDP's (a_trans, a_rot, a_grip) is the floor, not the ceiling.

[FATAL] Model B trained on hindsight ground-truth poses and deployed on Model A's predicted poses is a textbook covariate-shift cascade, and the design has no channel — gradient, reward, or signal — by which the error can be corrected in either direction.
  WHY: During training every (target_pose, RGB) pair is mutually consistent because the pose was hindsight-labeled from the same demo. At deployment the pose is 10-20 mm and several degrees off the object in the image. Model B has literally never seen an inconsistent pair, and its learned prior is 'the target is correct, servo to it,' so it drives into the object rather than servoing on vision. The literature quantifies this precisely: GHOST froze the low-level policy and swapped only the high level, moving fold-towel from 36.7-40% to 90% — ~50 points of task success sitting entirely in the handoff. GHIL-Glue's whole contribution is fixing only the handoff (filtering non-progressing subgoals + de-synchronizing augmentation) and it bought +25% on CALVIN and 54% -> 70% on a real robot. OpenHelix Table 6 is the extreme case: without pre-aligning the projector between the two separately-pretrained halves, every configuration scored 0/0/0/0/0. Because the interface is a hand-specified pose passed between two independently trained models, there is no gradient path: Model A never learns which poses Model B can actually achieve, and Model B never learns that this particular Model A undershoots.
  FAIL: Task: grasp a 25 mm-wide USB-C cable end lying flat on a desk. Model A predicts the grasp pose 12 mm off in +y and 5 degrees rotated (well inside its offline MSE budget). Model B, trained only on exact poses, closes the fingers 12 mm to the side of the cable and pinches the desk. Repeat 50 times: 50 identical failures, because the error is systematic, not random, and nothing in the system observes it. Separately, on a cheap serial-bus arm the gravity sag makes Model B undershoot 8 mm in +z near the workspace ceiling; a monolithic policy's vision encoder would learn to bias the command, but here A has no error signal from B and B cannot tell A its targets are 8 mm high in that region. The bias persists forever and looks like a perception bug.
  FIX: (a) Mandatory DAgger round on the interface: after A converges, roll A out on the training scenes, relabel, and retrain B on A's actual predicted-pose distribution. (b) Noise/perturbation augmentation on the interface during B's training, matched to A's measured error covariance. (c) A feasibility/progress filter between them (GHIL-Glue). (d) Add an upward channel B -> A (tracking error / reachability / confidence) that triggers replanning. (e) If at all possible, make the seam differentiable: pass a continuous latent alongside the pose and backprop through it (Helix), or freeze A and pre-align a projector (OpenHelix), or freeze the VLM and train only adapter+action model (GR00T N1.5: 43.3% -> 83.0% real GR-1 success).

[FATAL] The stated goal — split a fixed parameter budget across two models to improve task success and generalization — is the one claim the literature actively contradicts. Every measured hierarchy win decomposes into latency decoupling, cheap high-level data, or internet pretraining; none into capacity allocation. And splitting a local budget in half forfeits the largest measured effect in the field.
  WHY: The best-controlled tests all come out flat or negative on capacity: HiRT's real-world quasi-static average was 70.0 hierarchical vs 71.3 for a comparable monolith (the split was slightly worse); the systematic orchestration study measured naive hierarchy at 69.57% vs flat VLA at 69.63% on short-horizon tasks — an exact tie; OpenHelix's hierarchy added 63.9% -> 67.9% over an already-strong low-level-only policy; and pi0.5's own ablation found the 'implicit HL' variant (no runtime hierarchy, but hierarchy-shaped data in the training mixture) was second-best, with the authors concluding 'a significant portion of that benefit is already obtained simply by including subtask prediction data in the training mixture.' Meanwhile the effect that does move the needle is pretraining: random-init vs pretrained VLM is 77.5% -> 97.8% on LIBERO, ~20 points, an order of magnitude larger than any short-horizon hierarchy premium. And every split that works in practice is violently lopsided with a frozen internet-pretrained top: Helix 7B/80M (87:1), RoboDual 7B/20M trainable (350:1), pi0 3B/300M. Nobody splits 50/50, and nobody trains both halves from scratch on their own teleop data. Note the RT-Affordance ablation is the sharpest version of this: its pose-interface high level drops 77% -> 24% without ~750 cheap hand-annotated images and -> 11% without web co-training. The split's value there was data access, not parameters.
  FAIL: You collect 200 demos on your arm and split a ~1B budget as ~600M for A and ~400M for B, both trained from scratch locally. Evaluation: 'pick up the blue stapler' — an object not in your 200 demos. A monolithic pretrained VLA grounds 'stapler' from web pretraining and gets a plausible grasp pose; your from-scratch Model A emits a pose 6 cm off, somewhere between the two most-similar training objects. Model B faithfully executes it and grasps air. You now have two under-parameterized models, neither of which has ever seen the internet, and the failure is attributed to 'needs more data' when the actual cause is that the architecture forfeited the only 20-point lever available.
  FIX: Reframe the justification honestly: split for latency decoupling, for cheap non-teleop supervision at the high level, and for human-inspectable intervention — never for parameter allocation. Concretely: make Model A an internet-pretrained VLM (frozen or LoRA), make the split lopsided (A >> B, target 20:1 or more), and inject non-teleop data into A the way RT-Affordance did (web co-training + ~750 images collected in 1 h and annotated in 2 h) or HAMSTER did (1.2M off-domain samples). If A only ever sees your teleop episodes, you pay all of the split's costs and get none of its benefits.

[MAJOR] 'Absolute SE(3) waypoint' is the worst-measured action abstraction of the four canonical choices, and it is the one that maximally bakes in hand-eye calibration bias — a systematic, unobservable error that Model B cannot see and cannot correct.
  WHY: The only clean head-to-head I have (real single-arm platform, ACT-regression, average progress score) ranks: EE absolute 69.0%, joint absolute 77.3%, joint delta 88.0%, EE delta 89.6%. That is a ~20-point penalty for choosing absolute over delta, on the exact axis this design commits to. The same study finds chunk-wise delta beats step-wise delta by ~10 points with an O(1)-vs-O(k) noise-amplification argument. Independently, TRI's rigorous LBM study converged on relative SE(3) end-effector poses with 6D rotation as the action space, and GR00T N1.6's headline change was moving from absolute joint angles to state-relative action chunks. The calibration argument compounds it: typical hand-eye calibration lands at ~2.1 mm RMS translational and ~3.2 degrees rotational, with a payload/posture-dependent compliant-deflection term on top. An absolute pose command inherits that entire error chain as a fixed offset; a delta relative to the current measured pose cancels most of it, because both endpoints share the same bias.
  FAIL: Task: press a 12 mm button on a control panel. Hand-eye calibration is good (2 mm RMS), robot positioning adds ~1.5 mm, and the arm sags ~2 mm at full extension under its own weight in that posture. Absolute-pose commands accumulate all three into a ~4-5 mm systematic offset that varies with arm posture — so the button press works at the near edge of the workspace and reliably misses at the far edge. Model B cannot fix it: it was trained on demos where the same offset was baked into both the label and the observation, so it has learned the biased map, not the unbiased one. Switching the same system to chunk-wise deltas measured from the current EE pose removes the static component entirely.
  FIX: Change the interface from 'absolute SE(3) waypoint' to 'chunk-wise SE(3) delta relative to the pose at chunk start,' with 6D continuous rotation representation (never Euler, never raw quaternion — the wrap-around discontinuity is a free source of regression error). This is the single highest-value, lowest-cost edit to the whole proposal.

[MAJOR] The frame is left unspecified ('head/camera frame or base_link'), and on a robot with a moving head this is not a deferrable detail — a camera-frame pose is only meaningful together with the head extrinsic at the instant of image capture, so any inference latency turns head motion directly into target error.
  WHY: Camera-frame actions measurably win when extrinsics are known and static (OC-VLA: +8.0 sim-continuous, +13.8 sim-discrete, +10.0 real fixed-camera, and roughly half the degradation under a novel viewpoint: 14% vs 29%). But that entire result presumes an accurate, known, *static* T. With a moving head, T is time-varying and the target silently slides between A's inference and B's execution. The active-perception literature's response to exactly this is to fall back to a stable world/base frame for the action and predict head pose as a separate output. Note also that OC-VLA never studies sensitivity to extrinsic calibration error at all — so the +8 to +14 point benefit is measured under exactly the conditions this design does not have.
  FAIL: Task: grasp a mug handle while the head is panning at 20 deg/s to keep the object centered. Model A on a Mac mini takes ~250 ms (a 2-3B VLM at ~4 Hz), plus queueing. The pose was expressed in the camera frame at capture time t0; it is executed at t0+300 ms, by which point the head has rotated ~6 degrees. At 0.6 m from the camera that is ~63 mm of lateral target error. The grasp fails. Crucially, it fails *intermittently* — only when the head happened to be moving — which is the worst possible debugging signature and will be misdiagnosed as a perception or data problem for weeks. Even 1 degree of unstamped head error is ~10 mm at that range, which already exceeds the tolerance of any insertion, button press, or handle grasp.
  FIX: Fix the frame contract explicitly and in code: Model A predicts in camera frame (to keep the viewpoint-invariance benefit), you immediately transform to base_link using the head joint state *timestamped at image capture*, and Model B consumes base_link only. Never let a camera-frame target survive an inference delay. Log the head-state timestamp alongside every target and assert on staleness. If the head must move during manipulation, also measure the extrinsic error budget end-to-end before trusting any sub-cm task.

[MAJOR] On a redundant (7-DoF) arm a 6-DoF pose is an underdetermined command — it does not specify the arm — and on any arm the pose->joints map is inverse kinematics, which is already solved exactly, faster, and more accurately than any network Model B can be.
  WHY: Two separate problems. (1) Underdetermination: a 6-DoF pose leaves a 1-D null space per pose on a 7-DoF arm. Model B must invent the elbow, and its choice is unconstrained by anything Model A knows about the scene. The measured cost is enormous: real-world imitation on five confined-space tasks gives joint-space 96%, EE-pose-plus-explicit-redundancy (ERJ) 94%, and pure task space 8% — with 0% on 'take cup out of cabinet.' On unconstrained tasks ERJ matched task-space sample efficiency, so the redundancy term is free. (2) Reinventing IK: analytic IKFast solves a 6-DoF chain in ~5-50 microseconds exactly; TRAC-IK solves >99.8% of queries sub-millisecond vs ~96% for stock KDL. Learned IK is measurably worse — IKFlow reports millimeters of translation error and up to ~1.5 degrees rotation. And HDP's own ablation is the honest headroom estimate: a pose-outputting diffuser had a 24.55% IK error rate, i.e. a quarter of commanded poses were not realizable — and HDP's win came specifically from making the low level *kinematics-aware* (joint output distilled via differentiable FK), not from it being a neural net. Note also that essentially no published low-level policy outputs joint values: HiRT outputs EE deltas, RT-1/RT-2/RT-A output Cartesian deltas, TRI's LBM outputs relative SE(3), and GR00T N1.6 explicitly abandoned absolute joint angles.
  FAIL: Task: 'take the cup out of the cabinet.' Model A emits a geometrically valid grasp pose on the cup, 25 cm inside the cabinet. The 1-D null space of that pose includes elbow-up configurations that put the forearm through the cabinet's top shelf. Model B has RGB but has never been supervised on obstacle-aware redundancy resolution — the demos contain one elbow choice per pose and no explicit collision representation. It picks an elbow configuration that collides, the arm stalls against the shelf, and the joint controller either faults out or grinds. This is exactly the 8%-vs-94% result reproduced on your hardware.
  FIX: (a) On a 7-DoF arm, add one scalar to the interface: elbow arm-angle or the redundant joint (the ERJ formulation). It costs nothing on standard tasks and is the difference between 8% and 94% in confined spaces. (b) Build the trivial baseline first: Model A -> TRAC-IK / damped-least-squares with joint-limit and singularity avoidance and nullspace posture bias -> Cartesian impedance or position servo at 500-1000 Hz. Only reintroduce a learned Model B as an additive, clipped *residual* on top of that, and only if it measurably beats it. If Model B is doing IK, delete it and move the parameters into Model A — which is where GHOST's oracle ablation says the error actually lives.

[MAJOR] The pose interface has no channel for force, stiffness, or compliance, so it structurally cannot support any contact-rich task — and if the arm only accepts joint position commands, Model B cannot express compliance either, meaning the limitation is unfixable at both levels.
  WHY: VICES scoped this precisely: plain EE pose control is best on free-space path following, joint impedance is strong on constrained door opening, and variable EE-space impedance is clearly best on contact-rich surface wiping. The mechanism for precision assembly is stated bluntly in that literature: 'when the clearance between the peg and hole is small, relying solely on velocity or position controllers is insufficient, as the tolerance and the robot's precision are at the same level (sub-millimeter),' so small position errors convert into large interaction forces, which convert into jamming. The measured value of putting force in the loop is large: ForceVLA improves average task success +23.2% over pi0-based baselines (up to 80% on plug insertion); FAVLA reports 80.8% average, +38.0 points over a vision-only pi0 baseline. Even HAMSTER concedes its own interface 'cannot communicate nuances such as force or rotation.' A 6-DoF pose is strictly less expressive than the (pose, stiffness, damping) tuple that operational-space impedance control has consumed since 1987.
  FAIL: Task: insert a USB-C plug into a port (~0.2 mm clearance). Model A emits the correct final pose. Model B, commanding joint positions, drives to it stiffly. The plug is 0.4 mm off-axis — well within Model A's error budget and well outside the clearance. Position error converts to contact force, the plug jams at 3 mm depth, the joint controller keeps integrating error, and either the motors stall or the connector bends. There is no representation anywhere in the system for 'be soft in x-y, stiff in z, and spiral-search if you feel resistance.' The same failure mode appears on wiping (excessive normal force, motor stall or scratched surface) and door opening (arm fights the door's arc constraint).
  FIX: If any target task involves contact, add a compliance channel to the interface — at minimum a 3-level discrete flag (free-space / compliant-contact / stiff), better a 6-DoF stiffness vector (the VICES pattern). Feed F/T or joint-torque sensing into Model B's inputs. And check the hardware gate first: if the arm exposes only joint position commands, the compliance argument for a learned Model B does not exist at all and you should scope the tasks to free-space pick-and-place explicitly, in writing, before building anything.

[MAJOR] Giving Model B its own RGB stream pays the dominant compute cost twice, and on a single Apple-silicon box the two models serialize — so total latency is L(A)+L(B), strictly worse than one monolith of the same total size. The control-rate justification for the split is therefore void on the stated hardware.
  WHY: VLA-Perf's per-stage breakdown shows vision encoder + VLM backbone dominate latency (pi0 on RTX 4090: vision 4.02 ms + VLM 19.79 ms vs action expert 7.25 ms). Duplicating the vision front end doubles the expensive part on the platform least able to afford it — an M4 Pro is ~7 FP16 TFLOPS against an RTX 4090's ~165. Worse, MLX maintains a single Metal dispatch queue per process; concurrent models from separate threads crash with Metal assertions (ml-explore/mlx issue #3078, opened Jan 2026, closed without a fix), and multi-process MLX hangs stochastically under sustained GPU saturation. There is no CUDA-priority-stream or MPS equivalent on Apple silicon, so Model B's 20 ms request queues behind Model A's 250 ms command buffers and inherits its worst-case latency. Note how the systems that actually get rate decoupling do it: Helix runs S1 and S2 on *dedicated GPUs*; Gemini Robotics puts the backbone in the cloud. And the decisive counterfactual: SmolVLA got equal success rates, ~30% faster completion (9.7 s vs 13.75 s) and 2x throughput (19 vs 9 cycles) from asynchronous chunked inference on ONE model — roughly a 50-line change. OpenVLA-OFT made a 7B monolith 26x faster at action generation with 3x lower latency from decoding changes alone, then beat pi0 and Diffusion Policy at 97.1% on LIBERO.
  FAIL: You deploy on the Mac mini. Model A (2-3B VLM, int4) takes ~250-400 ms; Model B (200-300M with its own ViT) takes ~25-40 ms in isolation. Because both are MLX-on-GPU in the same process they serialize, and because Metal preempts only at command-buffer granularity, Model B's p99 latency is not 40 ms but ~300 ms — the length of Model A's forward pass. You measure a control loop at ~3 Hz with 100x jitter between p50 and p99, worse than the monolithic baseline you were trying to beat, and the jitter shows up as visible stutter and out-of-distribution jerk at chunk boundaries.
  FIX: (a) Do not give Model B a second full-resolution vision encoder — share Model A's visual features, or give B only proprioception + wrench + a small low-res wrist crop. (b) If you keep two models on a Mac, they must run on different execution engines: Model A in MLX on the GPU, Model B compiled to Core ML pinned to cpuAndNeuralEngine with GPU explicitly excluded — and you must verify ANE residency with the Core ML performance report, since Core ML silently falls back to GPU on unsupported ops. (c) Before any of that, exhaust action chunking + real-time chunking + async execution on a single model; that achieves the control-rate half of the goal with zero interface risk. (d) Run the >=500 Hz servo loop on the arm's controller or a Linux host, never on macOS.

[MODERATE] The interface passes a point estimate, discarding the multimodality and uncertainty of the high level — which is precisely where GHOST's oracle ablation says ~50 points of task success are being lost.
  WHY: Grasp pose prediction is genuinely multimodal: a mug affords a handle grasp and a rim grasp; a tool affords two ends. A regression or mean-prediction head over a bimodal target lands between the modes, producing a pose in mid-air. GHOST — which is the closest published analogue to this exact architecture and does predict 3D EE poses — deliberately outputs a per-patch Gaussian Mixture Model and renders it as a dense distance-field heatmap, and found dense heatmaps beat single-pixel binary masks because they give a denser supervisory signal. RT-Affordance likewise renders poses visually onto the image rather than passing raw numbers; RT-Trajectory's dimensionality ablation (2.5D 38% vs pure-2D 0% on 'Pick from Chair') shows that how you encode the spatial goal is decisive. A bare 7-vector also gives Model B no way to be cautious: it cannot distinguish 'I am confident this is the handle' from 'I am 50/50 between two grasps,' so it commits fully to a target that may be a mode-averaging artifact. This failure is invisible in offline MSE, which is part of why RT-H's ~20% offline MSE improvement did not translate proportionally to online success.
  FAIL: Task: 'pick up the frying pan.' The pan affords a handle grasp and a rim grasp; your 200 demos contain both roughly equally. Model A's regression head outputs the mean — a pose hovering ~7 cm above the pan's center, belonging to neither mode. Model B servos there with perfect fidelity and closes on nothing. Offline validation MSE looks fine because the mean minimizes L2 against a bimodal target; online success is 0% on that object and you will not find out until you run the robot.
  FIX: Emit a distribution, not a point: a GMM or a mixture-of-modes head, and deliver it to Model B by *rendering* it into the RGB Model B already consumes (a Gaussian heatmap / gripper overlay), following GHOST and RT-Affordance, rather than concatenating a 7-vector to the state. This also gives Model B a spatial, image-registered signal in the same coordinate system as its observations, which is why the heatmap encoding beat the alternatives. Pass the mode weights or an entropy scalar so downstream logic can gate on ambiguity.

[MODERATE] A single EE pose cannot express bimanual coordination constraints, whole-body posture, or retry/recovery intent — and with no termination or switching policy specified, the system will livelock on its first failed grasp.
  WHY: Bimanual: what matters when two hands hold one rigid object is the *relative* transform between them, not two independent absolute poses. Two independent targets each with 5 mm error compose into up to 10 mm relative error, which for a rigid grasp is either squeeze (internal force build-up, motor stall, object deformation) or gap (drop). No amount of per-arm accuracy fixes this; the constraint has to be in the interface. Whole-body posture (torso lean, head orientation) is likewise unrepresented — note Helix's S1 outputs target wrist poses *plus* finger flexion/abduction, torso and head orientation, all at 200 Hz, precisely because a wrist pose alone is not a whole-body command. Retry: a pose says 'go here'; it cannot say 'you already tried this and failed, try a different approach' or 'this is a regrasp.' After a failed grasp the scene is visually unchanged, so Model A emits the same pose and Model B, a deterministic function of (pose, joints, image), emits the same command — livelock. pi0.5 and Hi Robot both build explicit failure detection and replan for exactly this reason, and the systematic orchestration study found the switching/termination mechanism to be one of the decisive design variables (best hierarchy 67.1% vs naive 40.6% on long-horizon), with ablated hierarchies collapsing from ~95% to near zero.
  FAIL: Bimanual: 'carry the tray to the table.' Both hands grasp the tray edges. Model A emits two independent target poses per timestep; a 6 mm convergence error between them means the arms squeeze the tray, current limits trip on the shoulder joints, and the motion halts mid-transport. Single-arm retry: 'pick up the flat playing card off the table.' The gripper closes 2 mm too high and misses. The card has not moved, the image is identical, Model A emits the identical pose, Model B emits the identical command, and the arm attempts the same failing grasp indefinitely. There is nothing in the design that detects the failure, and nothing that would make the second attempt differ from the first.
  FIX: (a) For bimanual, put the relative transform in the interface as a first-class constraint, not two independent absolute targets. (b) Specify an explicit switching/termination policy up front — when is Model A re-queried? Event-triggered on gripper state change, on tracking error exceeding a threshold, on subtask success detection, on operator interrupt. OpenHelix's sweep shows high-level *rate* barely matters (running every step vs once per 60-step episode is a wash), so spend the design effort on triggers, not frequency. (c) Add a retry/attempt-count or intent field to the interface, and an upward failure signal from B so A can propose a different mode from its mixture on attempt two. (d) Add a workspace-bounds and reachability filter between the two models — a hallucinated pose from A becomes physical motion with no semantic check otherwise.

-- WHAT WOULD MAKE IT WORK --
  + Replace 'absolute SE(3) waypoint' with 'chunk-wise SE(3) DELTA trajectory' (8-16 waypoints, relative to the pose at chunk start, 6D continuous rotation representation). This single edit is worth ~20 points on the only clean head-to-head measurement (EE absolute 69.0% vs EE delta 89.6%) and cancels most of the ~2 mm / ~3 deg hand-eye calibration bias that an absolute target bakes in permanently.
  + Widen the interface to the minimum executable unit. Per waypoint: delta pose + continuous gripper aperture + dt/velocity scale. Globally: a compliance/stiffness channel (even a 3-level flag), a redundancy scalar (arm angle) on any 7-DoF arm, and a task-phase / attempt-count field. HDP's published interface is (a_trans, a_rot, a_grip) as the floor; ERJ's one extra scalar is the difference between 8% and 94% on confined-space tasks; force channels are worth +23.2% (ForceVLA) to +38.0 points (FAVLA).
  + Add a learned latent side-channel alongside the pose — the RoboDual pattern, which passes both a discretized action and task/action latents and whose ablation says both carry distinct information (+26.7% real-world over OpenVLA, strong performance at 5% of demonstration data). You keep the pose's interpretability and unit-testability while restoring bandwidth for phase, intent, object identity, and 'be gentle.'
  + Emit a distribution, not a point, and deliver it visually. Output a GMM / mixture over target poses and render it into the RGB Model B already consumes as a dense heatmap or gripper overlay (GHOST found dense heatmaps beat single-pixel masks; RT-Affordance and RT-Trajectory both render rather than pass raw numbers; RT-Trajectory's 2.5D-vs-2D result was 38% vs 0%). Model A predicts in camera frame (worth +8 to +14 points and roughly half the degradation under novel viewpoints, per OC-VLA); you transform to base_link immediately using the head joint state timestamped at image capture; Model B consumes base_link only.   + Train Model B on Model A's actual output distribution, not on hindsight ground truth. Concretely: noise-augment the interface during B's training using A's measured error covariance; then run a DAgger round — roll A out, relabel, retrain B.   + Do not train the two halves independently and bolt them together. The three viable recipes are: (1) train end-to-end with gradients through a continuous latent (Helix); (2) freeze the high level and pre-align a projector, then prompt-tune (OpenHelix — without pre-alignment, every configuration scored 0%); (3) freeze the VLM entirely and train only the adapter + action model (GR00T N1.5, which produced the largest reported gains: real GR-1 success 43.3% -> 83.0%). Add a workspace-bounds and reachability filter as a hard gate between the models.
  + Delete Model B in v1 and prove you need it. Baseline: Model A -> TRAC-IK (>99.8% success, sub-millisecond) with joint-limit, singularity and nullspace posture handling -> Cartesian impedance or position servo at 500-1000 Hz on the arm's own controller. Only reintroduce a learned Model B as an ADDITIVE, CLIPPED RESIDUAL on top of that classical output — which gives graceful degradation (residual -> 0 recovers the classical stack) and a tiny, fast network. A learned Model B is only worth its parameters if it does collision-aware redundancy resolution, contact/force adaptation, or visual servoing that cancels A's systematic bias. If it is doing IK, it is a 24.55%-error-rate approximation of a microsecond-exact solved problem.
  + Make the split lopsided and put the pretraining in the top half. Every working system is 87:1 (Helix 7B/80M), 350:1 (RoboDual 7B/20M trainable), or ~10:1 (pi0 3B/300M), with an internet-pretrained high level. Random-init vs pretrained VLM is ~20 points on LIBERO (77.5% -> 97.8%) — larger than any short-horizon hierarchy premium in the literature. RT-Affordance's predictor drops 77% -> 24% without ~750 images collected in ~1 h and annotated in ~2 h, and -> 11% without web co-training; HAMSTER trains its high level on 1.2M off-domain samples and its low level on 320 in-domain episodes. If Model A only ever sees your teleop episodes, you pay all the split's costs for none of its benefit.
  + Do not give Model B a second full-resolution vision encoder, and do not run both models as MLX-on-GPU in one process. Share A's visual features, or give B proprioception + wrench + a small low-res wrist crop. If two models must coexist on a Mac, A goes in MLX on the GPU and B goes to Core ML pinned to cpuAndNeuralEngine with GPU explicitly excluded — verified with the Core ML performance report, because Core ML silently falls back and reintroduces the contention you were avoiding.
  + Buy the control rate the cheap way first and measure. Implement action chunking + real-time chunking + asynchronous inference on ONE model (SmolVLA: equal success, ~30% faster completion, 2x throughput; OpenVLA-OFT: 26x faster action generation and 3x lower latency on a 7B monolith, then 97.1% on LIBERO). Chunk length is nearly free (5 -> 250 actions costs ~11% end-to-end latency) while denoising steps are expensive (10 -> 50 steps costs 5x), so use long chunks and few flow-matching steps, and never an autoregressive token action head (102x penalty). If that closes the rate gap, the split is unnecessary.
  + Build the three controls BEFORE the split, and power the evaluation. Controls: (a) monolith at matched total parameters and matched effective control rate; (b) Model A + classical IK/impedance with zero learned low level; (c) one model with an auxiliary target-pose prediction head and no runtime hierarchy — the pi0.5 'implicit HL' condition, which was second-best in their own ablation. On power: TRI needed 50 real rollouts per task per policy per condition and ~1,800 trials with Bayesian analysis and Bonferroni correction to separate policies, and HiRT's split-vs-monolith gap on static tasks was 1.3 points. A 10-trial A/B on one arm measures noise, not architecture.
  + Choose the evaluation regime where hierarchy can actually show a benefit, and say so up front. The premium appears on DYNAMIC scenes (HiRT 75% vs 48% with objects moving at 1 cm/s) and on LONG-HORIZON / reasoning-heavy tasks (+41.8 and +30.0 points respectively in the systematic orchestration study), and is an exact tie on short-horizon tasks (69.57% vs 69.63%). If the target is short-horizon quasi-static tabletop pick-and-place, the design is measured to buy nothing on success rate — decide that before building, not after.

[FATAL] There is no safety envelope anywhere in the described design — no joint-limit clamp, no velocity/acceleration limit, no force or torque threshold, no workspace bound, no reachability check, no watchdog, no e-stop — and Model B is the SOLE generator of joint commands, so every failure mode of either network is expressed directly as full-authority arm motion.
  WHY: Model A emits a pose with no feasibility or semantic check; Model B converts it to joint commands with no infeasibility check; neither network has a defined output range. Critically, there is no baseline controller underneath, so there is nothing to degrade *to*. This is the diagnostic that Model B is the command path rather than a corrector: ablate a biological cerebellum and you get ataxia (sloppy movement); ablate Model B and the robot is inert. Kawato's feedback-error-learning structure — learned term summed onto an always-on servo — has the property you want: a bad network output produces dysmetria, not a runaway. This design has the opposite property. And the high level is not reliable enough to be trusted unguarded: RT-Affordance's affordance predictor collapses from 77% to 24% without ~750 extra annotated images and to 11% without web co-training; GHOST measured its deployed high level at 36.7% against a 90% oracle. Roughly half of high-level outputs being wrong is the normal operating regime, not the tail.
  FAIL: Task: bin-picking from a cluttered tray. On a novel scene, Model A regresses a target pose 40 cm below the tray surface — an ordinary regression failure for a model in the 24–37% regime. Model B has no such pose in its training distribution, extrapolates, and emits joint deltas at the magnitude edge of its output range. The arm drives into the table at commanded speed. Nothing in the described pipeline can interrupt it: there is no force threshold to trip, no workspace box to violate, no velocity clamp, and no watchdog. On a 7-DoF arm there is a second, quieter version of the same failure — the elbow swings through the null space into whatever is beside the tray, because a 6-DoF pose does not determine the arm. The redundancy-aware action-space work measured pure task-space control at 8% success versus 96% for joint-space on exactly these confined-space tasks, with 0% on 'take cup out of cabinet', precisely because the redundant joint drifts unpredictably.
  FIX: Build a fixed, non-learned reflex layer BELOW both models, in code not weights, before either model exists: joint position/velocity/acceleration/jerk clamps, torque or motor-current threshold with automatic retract, workspace bounding box, self-collision check, finite-value assertion, and a deadman watchdog that holds last-good then ramps velocity to zero on missed deadlines. Then restructure Model B as a BOUNDED RESIDUAL added to TRAC-IK + impedance/PD, so that residual→0 recovers a fully working classical stack and a network fault produces dysmetria rather than a full-speed slew. Also add a reachability + workspace filter between A and B so a hallucinated pose is rejected as a typed error rather than executed.

[MAJOR] The interface is specified as 'Model A's output' with no timestamp, no head/base pose stamp, no validity horizon, no sequence number, and no defined behavior when A is late — and at a measured 500 ms p50 / 628 ms p99 A-period, staleness is the dominant error term, not a second-order effect.
  WHY: Three compounding problems. (a) A pose expressed 'relative to the head/camera frame' is meaningless without the head joint state at the image-capture instant; if the head or base moves between A's inference and B's execution, the target silently slides and no error is raised anywhere — the arm just goes to the wrong place. (b) Model B trained on synchronous demo-derived poses and deployed on 500–628 ms stale poses is textbook covariate shift. HiRT explicitly trains its low level on *cached stale* latents for exactly this reason. GHIL-Glue's entire contribution is fixing this handoff and it was worth +25% on CALVIN and 54%→70% on a real robot. (c) The staleness is nondeterministic: p50 500 ms vs p99 628 ms is a 128 ms swing, so Model B sees a jittering, unmodeled delay rather than a fixed one it could learn to compensate.
  FAIL: Task: 'pick up the red block' on a robot with an active head. At t=0 Model A runs on a head-frame image and emits a target pose. Over the next 500 ms the head pans 15° to track the scene (or the mobile base settles). At t=500 ms Model B receives the pose and transforms it using the *current* head state rather than the capture-time state. The commanded grasp lands 8 cm to the side of the block. The failure presents as a perception problem — the pose looks wrong — so you spend two weeks collecting more data for Model A and retraining it, and the success rate does not move, because the defect is a clock, not a network.
  FIX: Define the interface as a typed, versioned message carrying: capture timestamp, head/base joint state AT capture, frame id, sequence number, and a validity horizon. Convert to base_link immediately at Model A's output using the synchronized capture-time head state — never inside Model B. Specify the stale policy explicitly: if age > horizon, Model B holds the last valid target and decays commanded velocity to zero rather than extrapolating. Train Model B on replayed *stale* Model A outputs (a DAgger relabeling round) from day one, not on demo ground truth.

[MAJOR] macOS on this box is not a control host and cannot be made into one, and there is currently no control stack at all — so the 'high-rate cerebellum' half of the architecture has no place to actually run.
  WHY: Probed directly: kern.sched is 'edge', Apple's thread-migrating scheduler across 4 P-cores and 6 E-cores. There is no RT scheduling class, no PREEMPT_RT, no isolcpus/nohz_full, no way to pin a thread away from App Nap, thermal management, or E-core demotion. The only lever is thread_time_constraint_policy, which is soft real-time with no kernel guarantee. There is no SocketCAN on XNU and no EtherCAT master. ROS2 on macOS is REP-2000 Tier 3: source build only, no binaries, not CI-tested. The machine has no ROS2, no MLX, and no robot device node — only /dev/tty.Bluetooth-Incoming-Port and /dev/tty.debug-console. The nondeterminism is already visible in my own measurements: the fast model's p99/p50 ratio went from 1.28 solo to 1.89 under contention, and the cerebrum's p99 hit 628 ms against a 467 ms solo p50 — and that is with no camera capture, no I/O, and no display load competing.
  FAIL: Task: wiping a plate — a sustained-contact task requiring a stable setpoint stream. The 'cerebellum' loop is asked to run on this Mac at high rate. Mid-episode, with the GPU saturated by Model A, the loop thread is migrated to an E-core and two consecutive cycles are missed. Either the joint controller holds a stale setpoint — the arm stalls against the plate and normal force builds until something yields — or the queued commands burst out and the arm jerks across the surface. The contact-manipulation literature's own guidance is that setpoint rates below ~20 Hz produce force oscillation; this design delivers 4.7 Hz p50 with unbounded tail latency.
  FIX: Never run the ≥500 Hz servo loop on the Mac. Push it onto the arm's own controller or a small Linux/microcontroller host and have the Mac emit 20–50 Hz setpoints over wired Ethernet — the measured cost of that hop in the literature is ~0–4 ms, i.e. free. Keep the Mac as an inference server only, which is a role it is genuinely good at. This single change makes every macOS real-time objection moot without giving up the Mac. If the target tasks are contact-rich, also confirm the arm exposes a torque or variable-stiffness interface; if it only accepts joint positions, a learned Model B has exactly the same expressive power as IK + a position servo and cannot help on contact at all.

[MAJOR] Model B as specified is inverse kinematics plus a servo, learned — which is not merely wasteful but actively unsafe, because it destroys the infeasibility signal that classical solvers provide.
  WHY: 'Target pose + current joints → joint commands' is the IK signature. IKFast solves it analytically in 5–50 µs; TRAC-IK solves >99.8% of queries sub-millisecond versus ~96% for stock KDL. A network is ~3 orders of magnitude slower and mm-to-cm accurate instead of sub-mm. But the systems argument is sharper than the efficiency one: an analytic or QP solver RETURNS A TYPED FAILURE — 'no solution', 'infeasible', 'at joint limit', 'near singularity' — that you can branch on to replan, back off, abort, or re-query Model A. A regression network always returns a number. Near a singularity or beyond the reach envelope it returns a confident, plausible, wrong number with no runtime signal whatsoever. HDP measured a 24.55% IK error rate for a pose-outputting diffuser. And no deployed system does this: RT-1/RT-2/RT-Affordance output Cartesian deltas, HiRT outputs EE deltas, TRI's LBM outputs relative SE(3) with 6D rotation, and GR00T N1.6 explicitly ABANDONED absolute joint angles for state-relative chunks.
  FAIL: Task: reaching into a shelf for a mug near the edge of the workspace. Model A's target pose is 2 cm beyond the arm's reach envelope — comfortably within its error budget, given that hand-eye calibration alone contributes ~2.1 mm RMS translation and ~3.2° rotation before any prediction error. TRAC-IK would return failure in ~0.8 ms and you would replan or step the base. Model B instead emits the joint vector minimizing its training loss: the arm drives to full extension, the wrist parks against its limit, motor current climbs, and there is no error in any log. You diagnose 'Model B needs more data' and collect another 200 demonstrations, which cannot fix a geometry problem.
  FIX: Build the baseline first and measure it: Model A → TRAC-IK or damped-least-squares with joint-limit and singularity avoidance → impedance/PD at the arm's native rate. This is a weekend of integration, needs zero training data for the low level, and is what OpenVLA/π0/RT-2 deployments actually use. [MAJOR] The design has no failure-attribution mechanism, so when it underperforms you will not be able to localize the fault to Model A, Model B, the interface, staleness, or calibration — and the effect size being hunted is below the noise floor of any realistic trial count.
  WHY: Two separately-trained models, one non-differentiable interface, and no oracle harness means every failure has four indistinguishable explanations. The only method in the literature that actually localizes this is the frozen-one-side oracle swap: GHOST froze π_lo, swapped π_hi, and went 40%→90%, which is what proved the high level was the bottleneck. Without that instrumentation you are guessing. Compounding it, the effect you are looking for is tiny where the tasks are: HiRT's hierarchical-vs-monolithic gap on real quasi-static tasks was 1.3 points (70.0 vs 71.3, in the monolith's favor), and the systematic orchestration study found naive hierarchy at 69.57% vs flat VLA at 69.63% on short-horizon tasks — an exact tie. TRI needed 50 rollouts per task per policy per condition and 1,800 total trials with Bayesian analysis and Bonferroni correction to separate policies at all.
  FAIL: You finish both models and measure 45% on 'put the mug on the shelf'. Candidate causes: (1) Model A's poses are biased, (2) Model B cannot track poses it was not trained on, (3) Model B is choking on 600 ms-stale targets, (4) hand-eye calibration has drifted 3 mm since the demos were collected, (5) the elbow is colliding in the null space. Each hypothesis costs roughly a week to test and they interact. You run 10 trials per variant to move faster, which — given the true between-design gap is plausibly under 5 points — means every conclusion you draw is noise, and you will confidently ship the wrong one.
  FIX: Build the attribution harness BEFORE the models. (a) Oracle-A: replay demo ground-truth poses into Model B — upper bound on B in isolation. (b) Oracle-B: replace Model B with TRAC-IK + impedance and feed Model A's live poses — upper bound on A in isolation. (c) Log the interface with full timestamps and replay traces offline so failures are reproducible without the robot. (d) Choose long-horizon / reasoning-heavy / dynamic evaluation tasks, where the measured hierarchy premium is +30 to +42 points rather than 0, so the effect is above noise. (e) Power the evaluation at ≥50 rollouts per condition, or state up front that the experiment cannot conclude anything. The pose interface's one genuine, well-evidenced advantage over a latent is exactly this inspectability — budget for it as the deliverable rather than treating it as a side benefit.

[MODERATE] The data cost is not 2x, it is SEQUENTIAL and re-entrant: Model B's dataset cannot be collected until Model A exists, and every retrain of Model A invalidates it.
  WHY: Model B must be trained on Model A's error distribution, not on demo-derived poses, or it hits the handoff shift that GHIL-Glue measured at 16–25 points and GHOST's oracle gap put at 50 points. That forces the schedule train-A → roll out A → relabel → train B. Any change to Model A — more data, a different frame convention, a hand-eye recalibration — shifts the distribution Model B was fitted to, and Model B regresses silently, with no test that catches it because the two models have no shared CI.
  FAIL: Six weeks in, you improve Model A by adding 300 episodes and switching its output from head-frame to base_link. Model A's standalone metrics improve. End-to-end success on 'insert the plug' drops from 55% to 30%, because Model B was fitted to the old pose distribution and the old frame convention, and its contact behavior is the most distribution-sensitive part of the system.   FIX: Version and pin the interface schema explicitly; treat (A-version, B-version, calibration-version) as a single deployable artifact that cannot be mixed. [MODERATE] There is no validity, finiteness, or liveness contract on either model's output, and both are running fp16 on a Metal backend where deadline misses are already the measured norm rather than the exception.
  WHY: fp16 overflow in attention or normalization is routine, and flow-matching/diffusion samplers with data-dependent step counts can diverge. A NaN pose from Model A propagates into Model B, whose normalization layers will typically convert it into a finite but garbage output — which is worse than a NaN, because it will not trip a naive check downstream. Separately, the measured p99s (628 ms cerebrum, 289 ms ViT under contention) mean missed deadlines are normal operating behavior, so 'what happens when the message is late' has to be a designed behavior. Right now it is undefined, which means it will be whatever the last value in the buffer happens to be.
  FAIL: During a 20-minute unattended autonomous run of a repeated pick-and-place, a single fp16 overflow in Model A produces a NaN quaternion component. Model B's input LayerNorm maps it to a large finite value; the predicted joint vector jumps several radians from the current configuration; the arm executes a maximum-rate slew across the workspace. Post-hoc, the logs show one anomalous frame among ~2,000 and no exception was ever raised.
  FIX: Assert finite AND in-range at three points — Model A's output, Model B's output, and the servo input — and reject-and-hold on any violation rather than passing the value through. Add a step-magnitude limiter that rejects any joint command more than N milliradians from the current measured configuration. Add a deadman timer that ramps commanded velocity to zero after K missed deadlines. Log every rejection together with the input that caused it. This is roughly 50 lines of code and it is the entire difference between a logged anomaly and a damaged arm.
