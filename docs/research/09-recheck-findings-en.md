## Does wrist force/torque sensing as an input to the low-level policy (Model 2: head image + target pose in head-image frame + 14 joints + wrist F/T -> 14 joints) make a LEARNED low-level model genuinely justified — i.e. does it now have information that analytic IK + a classical impedance/admittance controller does not have and cannot use as well? And does F/T break the "learned IK shortcut" degeneracy?

VERDICT: Partially — the prior verdict was right about the mechanism but wrong about the conclusion, and it should be revised to "demote to residual and delete the image input," not "delete." Wrist F/T is genuine, non-kinematic side information: it is the only input in the whole system that carries contact state, object stiffness/weight, and slip, none of which are derivable from (target pose, joints). That materially changes the picture, and the empirical literature is unambiguous that force-as-INPUT to a position-outputting policy is transformative on contact-rich tasks — FACTR 21.3% -> 61.2% (naive) -> 87.5% (curriculum) on unseen objects with joint-position output into a PID controller; FILIC peg-in-hole 68% -> 90% in sim and +33 to +53 percentage points on four real tasks; sensorless-bilateral ACT nut-turning 0/5 -> 5/5 with force as input only. So the answer to "does it now have information IK cannot use" is yes. BUT three things sharply limit how much this rescues the proposed design. (1) The information-theoretic degeneracy is broken; the OPTIMIZATION degeneracy is not. A next-joint-angle MSE loss is ~99% explained by IK(target pose), the wrench contributes a small residual concentrated in a small minority of timesteps (FIRST measures force control as active in 84% of in-contact steps but only 2.9% of free-space steps), and every paper that measured it found the policy ignores force unless the architecture forces it not to — ForceVLA's naive force concatenation bought only +2.9pp (37.3 -> 40.2) versus +23.2pp for structured fusion, and FoAR's naive force-concat was actually WORSE than vision-only on one of two tasks. A flat concatenated input vector, which is exactly what the confirmed diagram specifies, is the configuration most likely to yield the ~+3pp outcome, and Model 2 is in the ForceVLA regime (pretrained vision encoder) not the FACTR regime (small ACT). (2) The output is bare joint positions with no stiffness, no wrench target, and no selection mask. The ALOHA mechanism is real — applied force ≈ Kp·(q_cmd − q_meas) — and FACTR/FoAR/FACTR-2 prove a position-output policy works, but it works for force-AWARE DISCRETE behavior (detect contact, switch mode, retry, adapt grip), not continuous force REGULATION. FACTR's own analysis says the policy "recognizes contact events and switches strategies, rather than continuously regulating applied force magnitude." Every system in the literature that achieved genuine regulation added something Model 2 does not have: an impedance inner loop (FILIC, 2 kHz), an explicit reference wrench + per-axis selection mask (Force Policy), a hybrid position-force controller (Tactile-VLA), or a hand-coded reactive stepping rule (FoAR, ε=0.006 m). (3) Rate. On the measured M4, Model 2 with a head image costs a full ViT pass — 62.75 ms solo, 214/289 ms p50/p99 under contention with Model 1 — i.e. a 3–5 Hz force loop, against DLS IK at 5.31 µs and a Robotiq FT300 that only outputs at 100 Hz anyway. A 3 Hz loop is not a force controller. The honest baseline is also much stronger than the proposal assumes: Minimalist Compliance Control (2026) gets sensorless admittance from motor current on position-commanded servo arms with no learning and no F/T sensor at all, taking egg-on-bread from 40% to 80%, and classical force control already solves well-specified insertion (100% at 0.1 mm clearance, 20 µm clearance in ~4 s). Net: the wrench earns a learned component, but it earns a SMALL, FAST, IMAGE-FREE residual on top of analytic IK plus admittance — not a monolithic image-conditioned network that reimplements IK.

### FINDINGS
- [inference] F/T is genuine non-kinematic side information — the information-theoretic degeneracy IS broken
    The prior review's core objection was that (target pose, joints) -> joints is a bijective kinematic map, so the model can only learn IK. A wrench is not a function of any kinematic state: identical (pose, joints) can correspond to free space, light contact, or jammed contact. It is the only input in the entire two-model system carrying contact state, environment stiffness, object weight/CoM, or slip. That objection is therefore genuinely retired. What remains is a different and weaker-but-still-serious objection about the training objective, not the input set.
    NUMBERS: Input dimensionality change: 12 (pose) + 14 (joints) = 26 kinematically-determined dims, plus 12 (two 6-axis wrenches) genuinely new dims. The 12 new dims are the only non-degenerate inputs besides the image.
    SRC: Reasoning over the confirmed I/O spec, corroborated by FILIC's finding that 'position-only observations miss key task-state information needed for reliable contact-rich control'
- [preprint] Force as INPUT ONLY (position output, no torque interface) demonstrably works — this is the strongest evidence for the design
    FACTR is architecturally near-identical to the proposal minus the image-frame target: images + external joint torques in, joint position targets out, executed by a PID controller on a Franka. No torque commands, no impedance. Force is input only. This is direct evidence that a position-commanding policy benefits enormously from force input. The sensorless-bilateral ACT paper independently ran the exact three-way ablation the question asks for and concluded 'force input was consistently beneficial, the effectiveness of force output was task-dependent' — force output even HURT on cucumber peeling.
    NUMBERS: FACTR on unseen test objects: ACT vision-only 21.3% -> ACT vision+force 61.2% -> FACTR (curriculum) 87.5% average across 4 tasks. Sensorless-bilateral ACT ablation (no force / force-input-only / force-in-and-out): nut turning 0/5 -> 5/5 -> 5/5; cucumber peeling 0/5 -> 3/5 -> 2/5; dual-arm pick-place 15/25 -> 14/25 -> 25/25.
    SRC: arXiv:2502.17432 (FACTR); arXiv:2507.06174 (Fast Bilateral Teleoperation and Imitation Learning Using Sensorless Force Control), Table III
- [preprint] But position-output policies do force-aware SWITCHING, not continuous force REGULATION — this is the load-bearing caveat
    FACTR's own behavioral analysis is explicit: the policy 'recognizes contact events and switches strategies accordingly, rather than continuously regulating applied force magnitude.' Its wins come from detecting contact onset and loss-of-contact (torque reverting to pre-lift values when a box is dropped) and retrying. FoAR outputs EE positions under 'simple position control' with 'no impedance, compliance, or hybrid force/position control deployed' — and then had to bolt on a hand-written reactive rule that steps the commanded position by ε=0.006 m toward the target whenever a force threshold is unmet. That hand-coded rule is doing the actual force regulation, not the network. The ALOHA mechanism (F ≈ Kp·(q_cmd − q_meas)) is real but gives fixed, isotropic, un-commandable stiffness set by the servo, with force resolution = Kp × position quantization.
    NUMBERS: FoAR reactive stepping increment ε = 0.006 m. FACTR reports no continuous force-magnitude tracking metric at all — only contact-event attention shifts and recovery success (13.3% -> 90% vs vision-only).
    SRC: arXiv:2502.17432 (FACTR) Fig. 7 attention analysis; arXiv:2411.15753 (FoAR) execution section
- [peer-reviewed] Naive concatenation of F/T — exactly what the diagram specifies — is the configuration most likely to yield near-zero benefit
    This is the single most important negative result for the proposal as drawn. ForceVLA ran the controlled comparison: the same pi-0 base with force naively appended gained almost nothing, while structured late-fusion MoE gained an order of magnitude more. FoAR's naive force-concat variant was WORSE than the vision-only baseline on wiping. The stated mechanism is consistent across papers: force is near-zero and uninformative for most of a trajectory, so gradient descent marginalizes it. Model 2 as drawn is a flat concatenation into a network with a pretrained vision encoder — structurally the ForceVLA regime (where naive fusion gave +2.9pp), not the FACTR regime (small ACT, where naive fusion gave +39.9pp). Variance across papers here is very high and that variance IS the risk.
    NUMBERS: ForceVLA: pi-0 vision-only 37.3% -> pi-0 + naive force 40.2% (+2.9pp) -> ForceVLA structured MoE 60.5% (+23.2pp). Fusion-point ablation: force injected BEFORE the VLM = 0% success (total collapse); linear projection pre-VLM 55%; concat post-VLM 60%; MoE post-VLM 80%; pi-0 baseline 45%. FoAR wiping score: RISE baseline 0.500 -> RISE force-concat 0.475 (worse) -> FoAR 0.875.
    SRC: arXiv:2505.22159 (ForceVLA, NeurIPS 2025) Fig. 5 and Table 3; arXiv:2411.15753 (FoAR)
- [preprint] The stated mechanism for force being ignored — and it is an optimization problem, not an information problem
    FACTR: 'contact force signals are typically less discriminative, often remaining near zero for extended periods when the arm is not in contact with the environment during an episode,' with policies 'overfit to using visual modality, effectively disregarding force data.' Attention analysis showed policies without curriculum stayed 80–90% focused on vision tokens. FoAR: naive fusion 'not only fails to fully leverage force/torque information but also risks introducing noisy force/torque data during non-contact phases, which can interfere with the policy's decision-making.' Force Policy: 'force is noisy or uninformative during non-contact motion and can pollute global decision-making.' Applied to Model 2, whose loss is next-joint-angle MSE and whose target is ~99% explained by IK(target pose), this predicts the model fits IK and treats the wrench as noise. Adding F/T removes the degeneracy in the INPUT SET but not in the OBJECTIVE.
    NUMBERS: FIRST quantifies the sparsity directly: force control active in 84 ± 10.8% of in-contact steps but only 2.9 ± 2.1% of free-space steps. Attention without curriculum: 80–90% on vision tokens.
    SRC: arXiv:2502.17432 (FACTR); arXiv:2411.15753 (FoAR); arXiv:2602.22088 (Force Policy); arXiv:2606.12406 (FACTR 2 / FIRST)
- [preprint] Three known mechanisms actually break the shortcut — all require changes not present in the diagram
    (a) Modality curriculum: FACTR progressively degrades the visual input (heavy Gaussian blur early, decaying), so gradients must use force to discriminate states; justified via an NTK argument. (b) Explicit contact-phase gating: FoAR's future-contact predictor dynamically routes force features only during contact; Force Policy learns a per-axis selection mask S ∈ {0,1}^6 choosing force vs position control per direction — which is literally the Raibert-Craig hybrid decomposition with a learned mask. (c) Data reweighting: FIRST upsamples pre-contact and contact segments. Notably, upsampling PRE-contact beat upsampling contact-only, i.e. alignment matters more than sustained contact. Any of these is a cheap addition to Model 2; none is implied by the diagram.
    NUMBERS: FACTR curriculum: 61.2% -> 87.5% (+26.3pp over naive force fusion) on unseen objects. FIRST: 0.818 vs 0.670 average task progress for pre-contact vs contact-only upsampling (+17% claimed over prior force-aware policies).
    SRC: arXiv:2502.17432 (FACTR); arXiv:2411.15753 (FoAR); arXiv:2602.22088 (Force Policy); arXiv:2606.12406 (FIRST)
- [measured] Decomposing (target pose, joints, wrench) -> joints: how much is IK and how much is not
    The map (target pose, joints) -> joints is exactly IK, and analytic DLS solves it in 5.31 µs on this machine with singularity robustness and bounded error. What the wrench adds decomposes into three parts: (1) contact-state estimation and phase detection — genuine, classical control cannot do it without a hand-written state machine, and this is where the learning wins are; (2) force regulation along constrained directions — this is precisely what admittance control does, provably and at 1 kHz, and a learned model at 3–5 Hz cannot do it as well; (3) implicit object-property inference (stiffness, weight distribution, slip) from wrench history — genuine, and demonstrably the source of generalization gains. So roughly: category 2 is a re-implementation of a solved classical problem; categories 1 and 3 are the real justification. The proposal is only justified to the extent it is capturing 1 and 3.
    NUMBERS: DLS IK 6x7: 5.31 µs (measured on this M4). Model 2 with image: 62.75 ms solo, 214/289 ms p50/p99 under contention — a 3.5–4.7 Hz p99 loop, i.e. ~40,000x the cost of the IK it would be replacing.
    SRC: Developer's own measured platform numbers; Raibert & Craig hybrid force/position decomposition as re-derived in arXiv:2602.22088
- [preprint] Category 3 (object-property generalization) is the most convincing real win, and it is measurable
    ALPHA-α/Bi-ACT ran the cleanest test of this: identical policy with and without force, evaluated on UNTRAINED objects of varying hardness, shape, and weight distribution. The largest gains were on liquid-filled objects with inconsistent, unobservable weight distribution — precisely the property that is invisible to vision and to kinematics but written directly into the wrench. The model modulates grip torque by object hardness. This is information analytic IK structurally cannot obtain and a fixed-gain admittance controller cannot exploit (it would apply the same law to every object).
    NUMBERS: Bi-ACT without force -> with force, untrained objects: eye cream 50% -> 100%; canele 80% -> 100%; glue jar 50% -> 80%; plastic bell pepper 70% -> 80%; soccer ball 80% -> 90%. Data at 1000 Hz joints, inference 70 Hz, commands 100 Hz.
    SRC: arXiv:2411.09942 (ALPHA-α and Bi-ACT), Table IV; arXiv:2401.17698 (Bi-ACT)
- [peer-reviewed] BE FAIR: classical force control already solves a large fraction of the target problem, with zero data
    Admittance/impedance control regulates contact force at 1 kHz with passivity/stability results, needs no training data, and generalizes to any object because it encodes a physical law rather than a fit. Raibert-Craig hybrid force/position exactly partitions the wrench into force-controlled and position-controlled subspaces — and the fact that a 2026 learned method (Force Policy) reproduces this decomposition and merely learns the selection mask is an admission that the decomposition itself is correct. Classical spiral/wiggle search with a force threshold is essentially a solved problem for well-specified insertion. Its honest limitations are: it cannot choose WHICH direction to make compliant when contact geometry is unknown, it needs an exact model or a good F/T sensor, hybrid switching can be unstable, and fixed impedance parameters do not adapt to unknown/varying environments.
    NUMBERS: Classical force-controlled peg-in-hole: 100% success at 0.1 mm clearance; 20 µm clearance in ~4 s; one reported 100% success with 3 s cycle time; 6 mm peg with 0.175 mm clearance in ~40 s with active force control. Variable impedance control: 100% on weak-stiffness peg-in-hole.
    SRC: Multiple classical peg-in-hole assembly surveys and papers surfaced in search (Park & Park partial spiral force trajectory; feature-based compliance control arXiv:2103.16003; robust force controllers arXiv:2003.03047)
- [preprint] The strongest fair baseline is sensorless admittance on position-commanded arms — no F/T sensor, no learning
    This is the baseline the proposal must beat, and it is much stronger than 'analytic IK.' Minimalist Compliance Control (2026) estimates external wrenches from actuator current/PWM plus the Jacobian, runs task-space admittance, and issues ordinary position commands to standard joint-position controllers — explicitly targeting low-cost servo arms. It requires no F/T sensor, no current-control interface, and no learning, and its authors argue directly against learned low-level controllers on safety grounds ('black-box nature of these policies often leads to sim-to-real discrepancies, resulting in a lack of safety guarantees'). If Model 2 does not beat this, the learned low-level model is not earning its cost.
    NUMBERS: Minimalist Compliance Control: egg-on-bread placement 80% vs 40% for position control; ball rotation 21° vs 2–3°; drawing position error 15.9 ± 5.1 mm (vs FACET 22.4 mm); force estimation error 0.69 ± 0.73 N from servo signals alone.
    SRC: arXiv:2603.00913 (Minimalist Compliance Control)
- [preprint] The residual architecture is now clearly the right answer, and F/T is what makes the residual non-trivial
    The prior review's fallback recommendation ('demote to a residual') was correct and F/T strengthens rather than weakens it. Structure: q_out = IK_DLS(target_pose, q_current) + Δθ(q, wrench, target). The analytic term handles the ~99% of the signal that is kinematics, exactly and for 5.31 µs; the learned residual is left with only the force-dependent correction — which is precisely the part the wrench explains, so the shortcut is removed BY CONSTRUCTION rather than by hoping the optimizer finds it. This also collapses the residual to a tiny MLP/GRU. TER-DAgger validates the pattern on precision insertion with a Cartesian impedance base at 1 kHz and a 2-layer, 256-dim, 8-head Transformer residual at 50 Hz.
    NUMBERS: TER-DAgger: 77.2% average success vs behavior cloning (ACT) 27.6%, finetuning 40.0%, human-guided DAgger 31.6% — from only 100 base + 50 corrective demos. Residual RL convergence reported at ~2 h single-GPU vs 4–6 weeks for end-to-end.
    SRC: arXiv:2603.04038 (Force-Aware Residual DAgger / TER-DAgger); arXiv:2106.04306 (Residual Feedback Learning for Contact-Rich Manipulation)
- [measured] The head-camera image in Model 2 is now the single worst element of the design and should be deleted
    With F/T confirmed, Model 2's job is contact-phase reasoning and force-dependent correction — none of which needs a 224x224 image that Model 1 already consumed. The image is what makes Model 2 cost a full ViT pass, contend with Model 1 for the GPU, and run at 3–5 Hz p99, which is fatal for anything calling itself force control. Without the image, Model 2's input is 12 (pose) + 14 (joints) + 12 (wrench) = 38 dimensions, i.e. a small MLP/GRU that runs at hundreds of Hz on the M4 CPU with no GPU contention. This one change converts Model 2 from redundant-and-slow to viable-and-fast, and it costs nothing that Model 1 does not already provide.
    NUMBERS: With image: 62.75 ms solo, 214/289 ms p50/p99 contended (3.5–4.7 Hz p99). Without image: 38-dim input, ~microseconds on CPU. Robotiq FT300 caps input at 100 Hz regardless, so a 100–200 Hz residual is the natural operating point; note Bi-ACT ran inference at 70 Hz and commands at 100 Hz, which is only achievable without a per-step ViT.
    SRC: Developer's measured platform figures; arXiv:2411.09942 (ALPHA-α) for the 70/100/1000 Hz reference stack
- [inference] DIAGNOSTIC: the decisive test is test-time wrench ablation, and it costs one eval run
    Ask directly whether the trained model uses the wrench. (D1) Freeze the model, replace the wrench input with zeros — and separately with a wrench shuffled from a different trajectory — at inference. If success rate and joint-trajectory MSE are statistically unchanged, the model has taken the IK shortcut. This is the single decisive test. (D2) Analytic-IK residual test: compute r = q_model − IK_DLS(target, q_current); if ||r|| sits at IK numerical tolerance the model learned nothing but IK. Then plot ||r|| against ||wrench|| — a force-using model shows correlation, a shortcut model shows none. (D3) Sensitivity: finite-difference or gradient-norm ∂q_out/∂wrench, computed SEPARATELY on in-contact and free-space timesteps; the correct signature is ~0 in free space and clearly nonzero in contact, and a flat profile means the wrench is being treated as noise. (D4) Held-out object properties: evaluate on objects with unseen stiffness/weight distribution (the ALPHA-α protocol) — force's payoff is generalization and it does not appear on training objects. (D5) Beat the honest baseline: analytic IK + sensorless admittance. Note that the field's standard practice is attention visualization, which FACTR and FACTR 2 both use and which is strictly weaker evidence than D1 — FACTR itself ran no zeroing ablation.
    NUMBERS: FACTR observed 80–90% vision attention without curriculum. FACTR 2 attention comparison: learned external torque showed clear attention spikes at contact events; raw joint current showed 'weaker and less event-aligned attention.' In FACTR's data, all methods performed similarly on TRAINING objects and diverged only on test objects — so D4 is mandatory, D1-only is insufficient.
    SRC: Synthesized; diagnostics D1/D3 follow standard modality-ablation practice (test-time zero-vector token replacement) and the Dropout-Proprioception literature on shortcut learning; D4 follows arXiv:2411.09942
- [preprint] Bilateral / force-feedback teleop during data collection is likely a precondition, not an optional extra
    This may be the highest-leverage unaddressed item. For a policy to learn force behavior, the DEMONSTRATIONS must contain consistent force behavior. Every study with large force gains collected data through a rig that fed force back to the operator: Bi-ACT and ALPHA-α used true bilateral control (θ_l − θ_f = 0, τ_l + τ_f = 0), the sensorless-bilateral work used a disturbance-observer bilateral rig, FACTR's leader arm provided force feedback, FACTR 2 scaled estimated external torque to the leader, and GELLO had to be explicitly augmented with force. In plain ALOHA-style unilateral teleop the operator cannot feel contact, so their applied forces are open-loop and inconsistent across demonstrations — the wrench channel then carries noise correlated with nothing the human intended, and no architecture will extract a policy from it. Note also that ALOHA 2's own literature flags that lacking force feedback 'prevent[s] users from sensing the geometric constraints of the environment, which is crucial for teleoperating contact-rich tasks.'
    NUMBERS: ALPHA-α bilateral rig cost: $8,951 total for 4 robots + 4 cameras, vs ALOHA $20,485 — 56% cheaper WITH force feedback, so this is not a cost argument against. FACTR 2 force feedback law: τ_feedback = K_f,p × τ_ext at 100 Hz.
    SRC: arXiv:2411.09942 (ALPHA-α); arXiv:2401.17698 (Bi-ACT); arXiv:2507.06174; arXiv:2606.12406 (FACTR 2); arXiv:2507.13602 (GELLO + force)
- [vendor] Sensor practicalities: 100 Hz ceiling, mandatory dynamic compensation, and ~2 N residual noise during motion
    Concrete numbers for the most likely sensor. The 100 Hz output rate is a hard architectural constraint: it is adequate for a 10–50 Hz policy and useless for a 1 kHz force loop, independently confirming that the fast loop cannot be the learned model. Gravity/inertia compensation is mandatory and non-trivial — you must identify 10 payload inertial parameters plus sensor offsets and subtract gravitational (orientation-dependent), inertial, centrifugal and Coriolis terms. Critically, the residual after good compensation is ~0.5 N static but ~2 N during motion, which exceeds many contact forces of interest — so the wrench is largely garbage during fast free-space motion. That is an independent, hardware-level reason to gate force usage on contact phase rather than feed it in flat. Filtering to suppress noise reduces bandwidth and adds delay. Drift requires a startup re-bias routine and periodic re-zeroing in a commercial product.
    NUMBERS: Robotiq FT300-S: ±300 N / ±30 Nm; noise SD 0.1 N (Fx/Fy/Fz), 0.005 Nm (Mx/My), 0.003 Nm (Mz) over 1 s; output 100 Hz; RS-485; temperature compensated only 15–35 °C; vendor-recommended detection thresholds 1–5 N and 0.01–0.12 Nm; relative measurement recommended only from 1 N. Price ~$1,950; ATI Gamma ~$3,200. Drift 0.05–0.2 N over 2 h with ambient temperature change. Post-compensation residual: <0.5 N static, ~2 N in motion.
    SRC: Robotiq FT 300 instruction manual specifications page and Robotiq accuracy knowledge base; wrist F/T gravity/inertia compensation literature (payload identification, PMC8777628)
- [preprint] You may not need to buy the wrist F/T sensor at all — current-based external force estimation is now competitive and free
    For a commercialization-intent bimanual system, two F/T sensors is $4k of BOM plus wiring, drift management, and a 100 Hz bottleneck. FACTR 2's NEXT trains an LSTM on 10 minutes of free-motion data to predict the torque required for gravity/friction/dynamics, then subtracts it from measured motor current; the residual is external contact torque. It beat a classical disturbance observer by 62.8% and on a Franka actually beat the arm's own dedicated torque sensor in free space. Minimalist Compliance Control gets 0.69 N from servo signals with no learning at all. The honest caveat: these give joint-space external torque, not a clean 6-axis wrist wrench — for fine fingertip forces, low-magnitude contacts near the payload noise floor, or clean torque-about-tool-axis (screwing), a wrist sensor is still materially better. But the decision should be made deliberately, not assumed.
    NUMBERS: NEXT L1 error during contact: 0.547 ± 0.348 Nm on Franka vs FILIC 4.395 ± 1.531 Nm and disturbance observer 1.471 ± 0.761 Nm. Free-space: NEXT 0.414 ± 0.278 Nm vs the dedicated external torque sensor's own 0.449 ± 0.208 Nm. On the $2,500 AgileX Piper: 0.018 ± 0.012 Nm vs 0.435 (FILIC) / 0.248 (DOB). Cost: 10 min of contact-free trajectories + 1 min training, 100 Hz, $0 hardware. Arms compared: AgileX Piper $2,500 vs Franka $30,000.
    SRC: arXiv:2606.12406 (FACTR 2 / NEXT); arXiv:2603.00913 (Minimalist Compliance Control)
- [inference] Frame mismatch: the wrench is in the wrist frame, the target pose is in the HEAD-IMAGE frame
    Model 1 outputs hand pose in the head-image frame, and Model 2 receives it in that frame. But the wrist wrench is measured in the sensor/tool frame. To use the wrench to regulate force toward the target, the model must relate the two, which requires head-camera extrinsics plus forward kinematics — and the diagram confirms head joint state is NOT an input. If the head can move at all, the head-image frame is time-varying and the required transform is unobservable from Model 2's inputs. Even with a fixed head, the model must learn a rigid transform it could simply be given. This is a concrete, fixable design bug that adds learning burden and reduces sample efficiency, and it is independent of the force question.
    NUMBERS: Missing information: 6 DoF of head extrinsics; head joint state is explicitly absent from the diagram. No reliable numbers on the resulting accuracy loss.
    SRC: Reasoning over the confirmed I/O spec
- [preprint] The gripper is absent from the diagram, yet a large share of the literature's force wins are GRIPPER force wins
    ALPHA-α's headline results — the 50% -> 100% jumps on liquid-filled and irregular objects — are grip-force adaptation, not arm force regulation. FACTR feeds gripper servo current into the same force token as arm torques. Tactile-VLA and Tabero predict fingertip force setpoints explicitly. The confirmed diagram has no gripper command anywhere, which means the system as drawn cannot capture the category of force benefit that is best supported by the evidence. Adding wrist F/T while omitting gripper force control captures the weaker half of the available gain.
    NUMBERS: ALPHA-α force-driven gains concentrated in grip modulation: eye cream 50% -> 100%, glue jar 50% -> 80%, canele 80% -> 100%.
    SRC: arXiv:2411.09942 (ALPHA-α); arXiv:2502.17432 (FACTR); arXiv:2507.09160 (Tactile-VLA)
- [preprint] Counter-evidence worth taking seriously: force input sometimes makes things worse
    The literature is not uniformly positive and the proposal should not be planned assuming it is. In ForceMimic's evaluation, 'the models that incorporate force as an input, including Force DP and Force+Hybrid DP, performed poorly' — the pre-contact motion was correct but once contact occurred they could not predict the right pose and force. FoAR's naive force-concat was worse than vision-only on wiping. ForceVLA's early force injection collapsed to 0%. The sensorless-bilateral pick-place task saw force-input-only at 14/25, slightly below the 15/25 no-force baseline. The consistent pattern: force helps a lot when the task is genuinely force-governed AND the architecture routes force to the contact phase; it is neutral-to-harmful otherwise. A plan should include the possibility that the measured delta is ~0 and a decision rule for what to do then.
    NUMBERS: ForceVLA early-fusion variant: 0% success. FoAR wiping: 0.500 (no force) -> 0.475 (naive force). Sensorless-bilateral pick-place: 15/25 -> 14/25 for force-input-only. Range of naive-concat effect across papers: −2.5pp to +39.9pp.
    SRC: arXiv:2410.07554 (ForceMimic); arXiv:2411.15753 (FoAR); arXiv:2505.22159 (ForceVLA); arXiv:2507.06174

### WHAT CHANGES
  > REVERSE the 'delete Model 2' half of the prior verdict; KEEP and STRENGTHEN the 'demote to residual' half. F/T is genuine non-kinematic side information and the prior conclusion was reached without it. But the correct target is not 'a learned low-level model' — it is q_out = IK_DLS(target_pose, q_current) + Delta(q, wrench, target_pose), with the analytic term absorbing the ~99% of variance that is kinematics. This removes the IK shortcut by construction instead of hoping the optimizer avoids it, and it is the only formulation where the wrench is guaranteed to be the residual's dominant explanatory input.
  > DELETE the head-camera image from Model 2's inputs. This is now the single highest-value change. It is what makes Model 2 cost a full ViT pass (62.75 ms solo, 214/289 ms p50/p99 contended = 3.5-4.7 Hz p99), contend with Model 1 for the GPU, and be too slow for anything called force control. Without it, Model 2 is a 38-dim input (12 pose + 14 joints + 12 wrench) MLP/GRU running at hundreds of Hz on CPU. Model 1 already consumed the image; Model 2 does not need it to do contact-phase reasoning.
  > ADD an explicit contact-phase gate or modality curriculum, and treat this as mandatory rather than an enhancement. The flat concatenation in the diagram is the exact configuration that gave ForceVLA +2.9pp (37.3 -> 40.2) versus +23.2pp for structured fusion, and that made FoAR's wiping worse than vision-only. Cheapest effective options in increasing cost: (a) FIRST-style reweighting of pre-contact and contact segments in the training mixture (pre-contact upsampling beat contact-only, 0.818 vs 0.670); (b) FoAR-style contact predictor gating the force features; (c) FACTR-style decaying visual/pose corruption curriculum (61.2% -> 87.5%).

Separately, two defects I consider larger than redundancy surfaced from the diagram: the pose is expressed in the HEAD-IMAGE frame with no head joint state anywhere in the I/O (Model 1's autoregressive rollout is ill-posed the moment the head moves), and wrist F/T cannot sense an elbow or forearm collision — the exact contact mode that confined-space 7-DoF operation creates.

- [measured] The arm angle (SEW/swivel angle) has an exact closed-form extraction from a recorded joint vector by forward kinematics — three lines of code, zero human labeling
    Definitive reference: Alexander J. Elias & John T. Wen, "Redundancy parameterization and inverse kinematics of 7-DOF revolute manipulators," Mechanism and Machine Theory 2024 (arXiv:2307.13122). Definitions: kSEW = pSW × pSE; nSEW = kSEW/‖kSEW‖ is the shoulder-elbow-wrist plane normal; eSW = pSW/‖pSW‖; a reference direction function ex = fx(pSW) with ey = eSW × ex fixes the zero. The ERJ paper's ERAngle uses the equivalent elbow-circle form pE = cE + rE·(tE·cos φ + bE·sin φ). The ERJ variant is even simpler: the redundancy scalar IS the recorded base joint angle j1, so the label is literally a column of the existing dataset.

- [peer-reviewed] An algorithmic singularity is PROVABLY unavoidable for any redundancy parameterization; the stereographic SEW angle reduces it from a full line to a half-line that can be placed outside the workspace
    Elias & Wen prove via the Hairy Ball Theorem that the unit vector field eCE(pSE) on the sphere of constant ‖pSW‖ cannot be continuous everywhere, so "there is discontinuity in the joint angle while the wrist travels along the sphere, corresponding to the algorithmic singularity." The conventional SEW angle (fixed reference vector er) is singular whenever pSW is collinear with er — a full line through the workspace, bidirectional. Near it, "being near an algorithmic singularity may result in dangerously large elbow movement, which is especially problematic for teleoperation," plus poor iterative convergence and loss of significant digits. Their stereographic SEW angle sets ex = kx/‖kx‖ with kx = krt × pSW, krt = (eSW − et) × er, converting two antipodal order-1 singularities into a single order-2 singularity — a half-line, which "for most robots ... can be chosen so that it goes into the structure holding the robot in place, meaning the singularity is out of the reachable workspace." Practical consequence: if you label ψ with the naive fixed-reference definition, your auto-generated labels will contain wild discontinuities in part of the workspace and the policy will learn garbage there. Use the stereographic variant, or use ERJ (base joint j1) which has no algorithmic singularity by construction.
    NUMBERS: Conventional SEW: singular on a full line (bidirectional, 2 antipodal order-1 singularities on the sphere). Stereographic SEW: singular on a half-line (1 order-2 singularity), placeable outside the reachable workspace. Unavoidability is a theorem, not an empirical claim.

## Is Model 2 structurally missing an input (head joint state / head pose) given that its pose target is in the HEAD-IMAGE frame while its output is arm joint angles in the arm base frame — or can it recover the head->base transform from the image, and how fragile is that?

VERDICT: Your deduction is directionally correct and the design is defective as specified — but the strong form of the claim ("Model 2 lacks the information, therefore the mapping is unidentifiable") is not quite right, and the imprecision matters because it changes the fix. Model 2 is not information-starved. It receives the 14 arm joints and the head image; the robot's own hands are usually visible in that image; therefore the head->base transform is in principle recoverable as B_T_H = FK_B(q_arm) · (H_T_hand_observed)^-1. That is exactly markerless eye-hand self-calibration (the iCub/Vicente line of work). So the transform is *weakly observable*, not absent. The defect is that it is observable only through a fragile, unsupervised, monocular channel that (i) fails precisely when the hands are occluded by the manipulated object or leave the FOV — which is when the head moves, (ii) is worst-conditioned along the optical axis, i.e. exactly the depth direction manipulation cares about, (iii) is never requested by any loss term, and (iv) will be out-competed during training by the far cheaper shortcut of memorizing a single constant B_T_H (or a task-phase-indexed lookup) whenever the training head is mostly static or head pose correlates with task phase. That shortcut is now empirically documented, not speculative: "Do You Know Where Your Camera Is?" (arXiv 2510.02268, ICRA 2026) shows BC policies infer camera pose from static background cues and that "this shortcut collapses when workspace geometry or camera placement shifts." The consequence is the worst failure class: excellent training and in-distribution validation, silent drift in the field. Quantitatively, at your measured p50/p99 latencies (214/289 ms) a modest 30 deg/s head pan injects 56–76 mm of lateral error at 0.5 m reach, versus the ~3 mm absolute accuracy DLR needed on Agile Justin for reliable manipulation. Separately — and this is a finding you did not ask for — the defect is not confined to Model 2: Model 1 predicts a *future* head-frame pose, and "head frame at t+k" is a different frame from "head frame at t" whenever the head moves, so Model 1's training labels are also corrupted unless reprojected (EgoVLA hits this exact problem and fixes it with world-frame camera poses). Conditions: this is NOT a defect, and head-frame is actually the empirically *superior* choice, if and only if the head is mechanically fixed or commanded to a fixed pose for the duration of each manipulation episode, with the same pose at train and deploy. The moment the neck is live, B_T_H becomes a latent exogenous variable and the design degrades from "correct and better" to "silently biased." The right fix is not to add head joints to Model 2 and hope it learns the transform — it is to do the transform analytically between the two models.

- [inference] The transform is weakly observable via the robot's own visible hands — not strictly missing — but observability fails exactly when it is needed
    Model 2 has q_arm (14) and the head image. FK_B(q_arm) gives the hand pose in base frame; the image gives it in head frame; composing them yields B_T_H. This is markerless eye-hand self-calibration, a real and established technique (iCub, Vicente et al.). So the naive 'unidentifiable' claim is too strong. But the channel degrades to unusable under four conditions that co-occur with head motion in manipulation: (1) the hand is occluded by the very object being grasped — the dominant regime in the second half of every reach; (2) the head turns to look at a target, which is precisely what pushes the hands out of a ~224x224 crop's FOV — so the transform becomes unobservable at the exact instant it changes; (3) monocular pose-from-hand is worst-conditioned in depth, the direction that determines grasp success; (4) nothing in the loss asks for B_T_H, so the network learns it only if training-data head variance makes the constant-transform shortcut lossy.

## What does each omission from the confirmed two-model I/O diagram (no gripper command, no timing/duration, no stiffness, no coordination mode, no inter-hand relative pose, no chunking) actually cost, quantified against published evidence — and what is the minimal set of fields that must be added?

VERDICT: Three of the four omissions are measured, published, large-magnitude failures, and one of them is not a degradation at all but a structural impossibility. The gripper command has nowhere to come from: Model 1 outputs 6-DoF pose, Model 2 outputs 14 arm joints, and the developer's "7-DoF x 2 = 14" is all arm — unlike ACT/ALOHA's superficially identical 14, which is 12 arm joints + 2 gripper joints (verbatim: "joint positions for two robot arms (7+7=14 DoF)" on "ViperX 6-DoF robot arms"). The system as drawn physically cannot command a hand to open or close, so grasping success is 0%, not merely degraded. Every published next-best-pose architecture of exactly this shape — HDP (a_high = (a_pose, a_grip)), PerAct, RVT — carries gripper as a first-class field alongside translation and rotation, so the developer's Model 1 is the only member of its own architecture family that drops it. Second, the per-step interface is the single largest measured degradation available in the literature: ACT's own ablation, verbatim, "performance improves drastically from 1% at k = 1 to 44% at k = 100" — a 44x swing from exactly the k=1 shape the diagram implies, and this is catastrophically worse on an M4 Mac mini where two contending vision backbones put the loop at roughly 2-3 Hz. Third, timing/duration: a waypoint with no time is not a trajectory, the low level can only infer velocity as Δpose divided by whatever inter-arrival interval the jittery inference loop produced, and approach velocity was measured to be linearly proportional to impact force (0.02–0.16 m/s, four repetitions each) — meaning the p50/p99 inference jitter of 214/289 ms directly modulates contact force by ~35% run-to-run on an identical commanded pose. Critically, the same paper found stiffness "has no significant effect on impact forces," so compliance cannot rescue a missing duration field. Fourth, inter-hand relative pose costs a measured 70% vs 30% on UMI's bimanual cloth folding, and it cannot be recovered by subtracting the two absolute poses because the training loss cannot distinguish a harmless common-mode error from an object-crushing differential error unless relative pose is separately supervised. Ranked by expected cost: gripper (unsatisfiable, hard zero) > chunking+timing (44x measured, and they are the same fix) > inter-hand relative pose (2.3x measured, and it is the bimanual premise) > stiffness/coordination mode (currently makes the newly-added wrist F/T sensor a dead input). The minimal addition is four fields: continuous per-hand aperture, a chunk of H future waypoints, a per-waypoint duration, and an explicit relative-pose field.

- [preprint] Gripper error is NOT self-correcting like arm error — it is a latch, and the policy cannot even observe that it failed
    This is the decisive asymmetry the developer needs to hear. Arm pose error is corrected next step by closed-loop feedback. Gripper error is a state transition that changes what the world contains. The measured mechanism: a binary gripper observation cannot distinguish 'grasp close' (object held) from 'empty close' (grasp missed) — 'the binary gripper state observation is identical (i.e., 1) for both the grasp close and empty close states.' The policy 'mistakenly treats the feedforward gripper state as a reliable indicator of the grasp state' and, on a missed grasp, 'incorrectly transitions to post-grasp actions like pull despite lacking a secure grasp.' So the failure is silent: the policy proceeds through the entire remaining trajectory carrying nothing, with no error signal. Adding real grasp feedback lifted disturbance-resilience success from 10-30% to 100%. Note this is an argument for a gripper *state input* as well as a gripper *command output*.
    NUMBERS: Disturbance-resilience success 100% with pseudo-tactile feedback vs 10-30% for baselines; grasp success under disturbance 80-90% vs 0-30%; overall task success 80-90% vs 10-45%.

- [peer-reviewed] Stiffness cannot substitute for the missing duration field — measured, and this closes the obvious escape hatch
    The natural objection is 'we'll just make the arm compliant and the timing won't matter.' - [inference] Relative pose cannot be recovered by subtracting two absolute poses — three independent reasons, one of which is decisive
    (1) Measurement: UMI did not subtract. Relative pose 'is enabled by our map-then-localize data collection scheme that constructs a scene-level global coordinate system'; demonstrations are 'relocalized to the same map, therefore sharing the same coordinate system,' yielding measured accuracy of 10.1 mm position / 0.8 deg rotation. It is a registered quantity in a shared frame, and UMI notes 'the effect of inter-gripper proprioception is particularly large when the visual overlap between two cameras is small' — an information-availability finding, not an arithmetic one. The developer's poses are in a monocular HEAD-IMAGE frame with no head joint state, so head motion injects correlated error into both terms. (2) Control: dual-arm literature requires the relative task to have its own gain — under perturbation, arms 'move in synchrony to maintain their relative posture and not exert force on the object they are carrying, acting compliantly in their absolute task but remaining stiff in their relative task.' Subtraction yields a number; it does not yield a controller with a separate stiffness. (3) Decisive — the training loss: a 5 mm error applied to both hands in the same direction is harmless; 5 mm in opposite directions generates internal force and crushes or drops the object. An L2 loss on two absolute poses assigns these identical penalty. The network is therefore never told that differential error matters more than common-mode error, so it has no gradient pressure to learn the invariant. This is why relative pose must be a supervised first-class field rather than a derived one.
    NUMBERS: UMI inter-gripper registration error: 10.1 mm position, 0.8 deg rotation. Closed-chain constraint requires relative transform held at desired value; violation generates internal forces.
    SRC: UMI arXiv:2402.10329 verbatim; dual-arm closed-chain control literature (Biomimetics 2026 reactive synchronized dual-arm controller; adaptive coordinated impedance control for symmetric bimanual tasks, Robotics and Autonomous Systems 2025). Reason (3) is my own analysis.

A head-mounted camera frame moves constantly, so the developer's design has the disadvantages of absolute representation with none of the stability that motivates it.

- [inference] Minimal set of fields that must be added — four, costing about 192 floats per inference
    MODEL 1 OUT, per hand, for each of H future steps: (a) pose — already present, but as a chunk of H rather than a single step; (b) aperture — one continuous scalar per hand for parallel-jaw, or an N-vector if multi-finger, explicitly continuous not binary; (c) dt — one duration scalar per waypoint, which is the field that converts a waypoint list into a trajectory and gives the low level a defined approach velocity; (d) inter-hand relative pose — an explicit 6/7-DoF field, supervised with its own loss term, not derived by subtraction. MODEL 2 IN: accept all of the above. ## Under the CONFIRMED I/O spec (both Model 1 and Model 2 consume the head camera image; Model 2 additionally consumes wrist F/T + 14 joints + hand pose), does the compute verdict for an Apple M4 Mac mini 32GB still hold? Specifically: achievable Model 2 Hz solo and under GPU contention, CPU viability with a vision encoder and its crossover point, the saving from sharing one vision encoder, and whether the classical bimanual 7-DoF IK path stays microsecond-scale.

VERDICT: The confirmed spec is comfortably feasible, and the previous pessimism about GPU contention was directionally right but led to the wrong fix. The decisive measured fact is that Model 2 must not live on the GPU — but it does NOT need to be stripped of its vision encoder. With Model 1 (263.8M cerebrum, ViT-B/16@224 + 16L d=960 trunk) saturating MPS flat-out, a Model 2 carrying its OWN ViT-S/16@224 encoder plus the 14-joint + 6-wrench + 14-pose MLP runs on the CPU at 59.5 Hz p50 / 50.4 Hz p99 / 28 Hz worst-case, while Model 1 only drops from 4.45 to 4.2 Hz. The same Model 2 placed on MPS collapses to 15.5 Hz p50 / 11.5 Hz p99 and drags Model 1 down to 3.4 Hz — mutual destruction. The reason is that batch-1 inference on M4 is dispatch-bound, not FLOP-bound: a batch-1 ViT-B forward achieves only 0.565 of the 3.78 TFLOPS the GPU can sustain (15% utilization), and a single isolated MPS dispatch costs ~179 us round-trip versus ~1 us on CPU. Consequently the CPU (1.90 TFLOPS peak via AMX/Accelerate) beats MPS at every Model 2 size tested, in fp32 against the GPU's fp16 — ViT-B 44.7 ms CPU vs 64.2 ms MPS. Sharing one vision encoder between the two models saves only 14.6 ms/cycle (6.0% of an MPS lockstep cycle, 9.5% on CPU) and should NOT be adopted as a compute optimization, because it couples Model 2's vision rate to Model 1's 4-5 Hz; its real value is different, namely that a Model 2 head running on cached tokens costs 0.197 ms (5076 Hz p50 / 4149 Hz p99) and gives you a >1 kHz F/T reflex path essentially for free. The classical path is a non-issue: bimanual DLS-with-null-space IK measured 16-21 us p50 and under 28 us p99. The newly confirmed F/T input is free — 6 extra scalars into an MLP, unmeasurable. Thermal state was clean throughout (no warnings recorded after ~15 min sustained load), so all numbers are un-throttled steady state.

  > Drop any plan to co-schedule both models on the MPS GPU. Measured: Model 2 falls to 15.5 Hz p50 / 11.5 Hz p99 and Model 1 to 3.4 Hz. This is the single highest-value correction.
  > Reverse the reason Model 2 goes on CPU, and widen the conclusion. The prior recommendation likely put Model 2 on CPU because it was assumed small/proprioception-only.   > Reframe encoder sharing as a cached-token reflex path if you want it at all. Model 2's head on cached tokens is 0.197 ms (5076 Hz p50, 4149 Hz p99, 1965 Hz worst) on one CPU thread — that is how to make the F/T loop fast, not by sharing to save FLOPs.
